# 프로젝트와 개발 용어

용어의 뜻을 확인하거나 새 개념에 이름을 붙일 때 읽는다. 도메인 개념의 이름·뜻이 달라지면 관련 문서와 함께 갱신한다. 동작 요구사항과 구현 결정은 각각 PRODUCT·DESIGN·ARCHITECTURE에서 관리한다.

## 프로젝트 용어

| 용어 | 정의 | 구분할 표현 |
| --- | --- | --- |
| 준비된 사진 | 프로토타입에서 촬영 입력을 대신하는 미리 선정한 사진 | 갤러리에서 정답 사진 찾기를 필수 과업으로 만들지 않음 |
| 장면(Scene) | 준비된 사진과 그 안의 지원 대상·영역을 묶은 테스트 단위 | 실제 GPS 위치 감지와 구분 |
| 대상 | 방문객이 이름이나 설명을 확인하려는 눈앞의 장소·사물 | 위치 좌표 자체와 구분 |
| 후보 | 대상일 가능성이 있어 사용자가 비교할 수 있도록 제시한 항목 | 확정된 인식 결과로 부르지 않음 |
| 부분(Part) | 건물의 문양·문·바닥 등 사용자가 알아보려는 세부 요소 | 종류의 일반 설명과 특정 위치 요소의 설명을 구분 |
| 지원 영역(Region) | 준비된 사진 안에서 사전 연결한 부분의 좌표 범위 | 모델이 자동 탐지한 영역이 아님 |
| 선택한 대상 | 사용자가 전체·부분 지정 또는 후보 확인으로 고른 대상 | 시스템이 정답을 검증했다는 뜻은 아님 |
| 관련 질문 | 선택 대상에 연결해 미리 준비한 질문과 답변 진입 항목 | 자유 질문·생성형 답변과 구분 |
| 호기심 카드 | 홈에서 장면 속 한 대상을 더 살펴보게 제안하는 선택적 카드 | 실제 위치·시선을 추정한 알림이 아님 |
| 테스트 설정(Preset) | 장면·방문 맥락·카드 표시 조건을 사전 지정한 묶음 | 참여자 정답 안내·사용자 계정과 구분 |
| 설명 | 선택한 대상의 명칭·의미에 관한 내용 | 출처와 연결해 확인할 정보 |
| 출처 | 설명이나 자료의 근거를 확인할 수 있는 참조 | AI의 추측·확률과 구분 |
| POI | Point of Interest. 탐색하거나 방문할 관심 지점 | 사진 안의 모든 사물이 POI인 것은 아님 |

## 개발 문서를 읽기 위한 용어

이 절은 사람이 문서를 읽기 위한 설명이다. 도메인 모델링 시에는 위의 프로젝트 용어를 사용한다.

| 용어 | 뜻 |
| --- | --- |
| 명세(Spec) | 만들 기능의 목적·범위·기대 행동·검증 기준을 정리한 문서 |
| PRD | Product Requirements Document. 제품 요구사항 문서. 이 프로젝트에서는 제품 공통 범위와 기능별 명세를 구분해 관리 |
| Issue / ticket | 목적·완료 기준·진행 상황을 관리하는 작업 기록 |
| PR | Pull Request. 코드·문서 변경을 검토하고 병합하기 위한 기록 |
| 완료 기준(DoD) | Definition of Done. 완료라고 판단하려면 충족해야 하는 공통 조건 |
| 인수 조건(Acceptance criteria) | 특정 작업에서 사용자가 관찰할 수 있어야 하는 결과 |
| Vertical slice | 여러 계층을 연결해 독립적으로 확인할 수 있는 작은 사용자 흐름 |
| ADR | Architecture Decision Record. 중요한 설계 선택과 이유의 기록 |
| TDD | Test-Driven Development. 기대 동작을 확인하는 실패 테스트에서 시작하는 개발 방식 |
| CI | Continuous Integration. 변경을 통합할 때 정해진 검사를 자동 실행하는 체계 |
| 디자인 토큰 | 색상·간격·글꼴 등 재사용할 시각 값을 이름으로 관리하는 단위 |

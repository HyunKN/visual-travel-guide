# 완료 기준과 검증

상태: 검증 계획. 아래 항목의 통과를 주장하는 문서가 아니다. 작업 시작·검증 시 읽고 완료 기준이나 검사 방법이 바뀔 때 갱신한다.

## 공통 완료 기준

검사의 실행·재실행 여부는 [핵심 기능 변경 시에만 재검사](DEVELOPMENT.md#핵심-기능-변경-시에만-재검사)를 따른다. 기존 통과 근거를 재사용하며, 아래 완료 기준만을 이유로 같은 자동/수동 검사를 반복하지 않는다.

2026-11-14 사용자 범위 결정: 현재 App 개발·인수에서 TalkBack 수동 검사를 제외한다. 제외를 통과 실적으로 기록하지 않으며 기존 큰 글자·터치 영역·버튼 이름·포커스 지원 코드는 유지한다. 기존 문서/Issue의 과거 TalkBack 검사 요청은 이 결정으로 대체한다.

- 작업 Issue 또는 사용자 요청의 행동을 실제로 확인한다.
- 관련 자동 검사와 수동 검사를 구분해 결과를 남긴다. 실패와 미실행을 구분한다.
- 변경한 동작과 문서가 일치하고 문서 영향 여부가 기록돼 있다.
- 정상 흐름과 그 작업에서 다룬 빈 상태·오류·복구 경로를 확인한다.
- 미확인 항목과 제한이 명시돼 있다. 필수 확인 항목이 남으면 전체 완료로 표시하지 않는다.
- [구현 전 통과 조건](DEVELOPMENT.md#구현-전-통과-조건)의 적용·간소 적용 근거와 실제 변경이 일치한다. 구현 중 문제·설계·평가 기준이 달라졌으면 해당 결정을 갱신한다.

## 수업 제출 문서 작성과 검수

2026-11-02 사용자 요청: Sprint 제출 피드백을 이후 문서 작성·검수에 적용하고, 같은 위험이 보이면 먼저 경고한다. 문서 간 합계·목록이 일치하는지와 계획의 현실성·실제 수행 근거가 충분한지를 각각 확인한다.

1. **제출 기준과 범위:** 최신 양식·수업 일정·평가 지침과 사용자가 실제 제출한 버전을 확인한다. 제출 당시 평가에는 이후 개발 실적을 섞지 않는다. 원본 안내문·검증 규칙은 보존하고 지정된 답변란을 수정한다.
2. **우선순위에서 Sprint 선택:** 요구·가치 변경의 근거를 검토해 Product Backlog 우선순위를 정한 뒤 Sprint 범위를 선택한다. 계획에 넣은 목록을 정당화하려고 PB 순위를 거꾸로 맞추지 않는다. 범위 변경 이유·의존성·감당할 근거를 기록하고, 급격한 SP 확장은 완료 실적과 가용 시간으로 뒷받침되지 않으면 경고한다.
3. **현실적인 Capacity:** 시험·행사·다른 과제의 영향을 날짜별 가용 시간·일수에 먼저 반영한다. 모든 주말을 최대 시간으로 계산하거나 예비만으로 일정 손실을 대신하지 않는다. 초기 가정과 재계획 시점의 잔여 가용 시간을 구분한다.
4. **추정과 Spike:** AI 활용만으로 연동·데이터 준비·학습·검증·수정 시간이 짧아진다고 가정하지 않는다. 불확실한 모델·외부 API·인증 연동은 수업 지침의 2h Spike처럼 시간을 제한한 탐색과 본 구현을 구분한다. Spike는 완성 보장이 아니라 성공/실패·막힌 원인·다음 추정 근거를 남기는 작업이다. Task는 내용과 불확실성에 맞게 나누며 짧은 시간 안에 준비·구현·평가를 과도하게 묶으면 경고한다.
5. **SP·시간·예비:** 시간/SP 가정은 단위와 근거를 밝히고 Task 합계÷선택 SP를 다시 곱해 실행 가능성을 검증했다고 하지 않는다. 첫 Sprint 종료 후 실제 완료 SP와 실제 투입 시간을 다음 추정에 활용한다. 예비는 해당 수업의 허용 범위를 따르고, 범위를 맞추기 위해 작업량을 늘리거나 추정치를 임의 조정하지 않는다.
6. **일별 기록 일치:** Task 상태·잔여 합계, Burndown 실제값, Daily Scrum의 Task ID·실제 장애 요인이 같은 사실을 가리키는지 대조한다. 미집계 사유를 정직하게 적는 것과 매일 실제값을 갱신한 것은 구분한다. 초기 재계획 잔여를 실제 소진 실적으로 해석하거나 과거 완료·소요 시간을 추측해 채우지 않는다.
7. **완료와 체크:** AC의 Task 연결과 실제 통과를 구분한다. 미실행은 미판정, 검사 실패는 F로 기록하고 ‘P(확인 대기)’를 쓰지 않는다. 필수 리뷰·병합·실제 데이터 검증을 포함한 DoD가 남으면 완료로 처리하지 않는다. 모든 AC·DoD를 충족한 Story만 완료 SP에 합산하고, 자가점검은 실제 확인 근거에 따라 체크한다.
8. **문서 간 의미와 선정 근거:** Goal은 사용자에게 남는 하나의 가치로 쓰고, 표의 문장뿐 아니라 붙은 범위 설명까지 관련 문서와 대조한다. Story 선택 이유에는 가치·의존성·위험의 구체적 근거를 적는다. 기술은 해결할 요구·비교한 대안·선정 이유·절충·남은 검증을 연결한다.
9. **새 아이디어의 니즈:** 다른 앱의 인기나 게임 사례는 발상·참고 근거다. 새 대상·상황에서 누가 왜 원하는지, 기존 대안으로 충분한지, 실제 발언·행동·반대 사례를 확인해 기록한다. 친구와 일상 공유에 대한 관심을 낯선 방문객의 장소 경험 공유 수요로 옮겨 확정하지 않는다.

위험이 있으면 완료·제출 가능하다고 결론내리기 전에 **해당 파일·절과 현재 값 → 위험한 이유 → 필요한 근거 또는 수정 선택지**를 짧게 알린다. 합의한 값·범위·완료 기준은 임의로 바꾸지 않는다. 단순히 서로 맞는 문서라는 이유로 현실적인 계획이나 검증 완료라고 보증하지 않는다.

당시 피드백 사례: 17 SP에서 50 SP로의 확장, Task 47h에서 역산한 0.94h/SP, 행사 미차감 Capacity 60h, 21.7% 예비, 첫 주 미집계 기록은 재검토 대상으로 지적됐다. 교수는 핵심 4개 Story·17 SP로 범위를 되돌리고 ONNX·인증을 각각 2h Spike로 확인한 뒤 재추정하도록 요청했다. 이는 과거 제출 평가이며 현재 계획을 자동 변경하거나 이후 모든 Sprint의 SP 상한으로 적용하지 않는다.

## 첫 흐름의 검사 시나리오

구체적인 기능 판정 F01~F13와 G01~G10, 사람 관찰 S1~S5, 개입·미지원 기록은 [프로토타입 TESTING](prototype/TESTING.md)과 [보완 설계](prototype/FLOW_EXTENSION_DESIGN.md)가 상세 원본이다. 기능 검사와 사람 관찰의 완료를 구분한다.

반복해서 사용할 제작자 기능 확인→첫 사용 관찰→보조 과업→문제 기록→수정 재확인 절차와 1차 조사 근거는 [QA 방법](prototype/QA_METHOD.md)에 둔다. 사람이 읽을 방법은 [HTML 안내](prototype/QA_METHOD.html), 실제 수행·기록은 [화면 순서별 테스트지](prototype/TEST_GUIDE.html)를 사용한다. 목표와 시작 화면은 명확하게 제시하고, 첫 사용 관찰 중 정확한 조작 순서는 진행자 참고로만 둔다.

| 입력·행동 | 기대 결과 | 확인 방식 |
| --- | --- | --- |
| 준비된 장면 A에서 전체 또는 부분 지정 | 해당 대상의 미리보기·기본 설명, 모호할 때만 후보 | 데이터 연결 검사 + 화면 확인 |
| 후보 1 선택 후 후보 2로 변경 | 제목·설명·출처가 모두 후보 2와 일치 | 상태 전환 검사 + 화면 확인 |
| 사진 A에서 B로 변경 | A의 선택·설명이 남지 않음 | 상태 전환 검사 |
| 설명에서 대상 수정으로 복귀 | 같은 장면에서 전체/부분 재선택 가능 | 수동 흐름 확인 |
| 영역 밖 또는 후보 중 해당 없음 | 임의 대상에 매칭하지 않고 재지정 가능 | 화면 확인 |
| 관련 질문 선택·질문 없음 | 해당 대상 답변 또는 명확한 지원 한계 | 상태·화면 확인 |
| 호기심 카드 선택 | 카드와 같은 대상·질문의 설명 표시 | 자료·화면 확인 |
| 설명·출처가 누락된 테스트 자료 | 누락을 표시하고 임의의 내용을 채우지 않음 | 데이터·화면 확인 |
| 실제 스마트폰에서 첫 흐름 수행 | 핵심 행동이 가려지지 않고 설명을 읽고 선택 변경 가능 | 사용자 또는 기기 접근이 있는 검증자 |
| 웹을 선택했다면 키보드로 조작 | 항목에 접근·선택 가능하고 포커스를 식별 가능 | 키보드 수동 확인 |

프로토타입의 자료·좌표·상태 검사는 Node test runner, 콘텐츠 파일 검사는 Node 표준 모듈로 실행한다. 실제 명령은 [실행 안내](../prototype/README.md), 수행 범위는 [검증 기록](../prototype/VERIFICATION.md)에 있다. 실제 기기가 없으면 화면 크기 에뮬레이션 결과와 실기기 미확인을 각각 기록한다.

## 제품 가설 확인

대상 선택, 설명 이해, 관찰된 혼란·개입·미지원 질문을 기록한다. 문양·구조물을 스스로 탐색한 경우와 진행자가 지정한 과업을 구분하고, 카드 탭과 실제 장면 재관찰을 구분한다. 첫 소수 관찰은 일반 성공률이나 효과 추정이 아니다. 향후 기존 방식과 비교할 때는 과업·기기·자료·순서와 학습 효과를 통제하고 기준선을 함께 둔다.

첫 흐름의 사용성 확인은 자동 인식 정확도나 현장 이동 안내 효과를 검증하지 않는다. 해당 기능을 도입할 때 데이터·권한·네트워크·실기기 조건과 실패 복구 시나리오를 추가한다.

## 첫 진입과 첫 유용한 결과 검증

[제품 구조 §2.2](ARCHITECTURE.md#22-핵심-흐름-1--첫-진입에서-첫-유용한-결과까지)와 US-01 AC-01~03을 확인한다. 기능 검사와 첫 사용자 관찰은 서로 대체하지 않는다. 아래는 계획이며 아직 실행 결과가 없다.

**제작자 기능 확인:** 첫 화면에서 실제 제공 경로만 진입 가능한지, 예시가 예시로 유지되는지, 첫 결과의 대상 ID·설명·출처가 일치하는지, 예시→실제 입력 전환 때 이전 결과가 지워지는지 확인한다. 홈 열람 시 권한 거부·모델 준비가 시작 화면을 막지 않아야 한다. 취소·자료 누락·모델 실패에서도 사용 가능한 다른 경로로 이동할 수 있어야 한다. 미구현 기능 약속·예시를 실제 인식으로 표현·다른 대상 설명 연결은 필수 실패로 처리한다.

**첫 사용 관찰:** 사전 사용법 안내 없이 ‘경복궁을 관람 중이며 눈앞 건물이 궁금한 상황’과 ‘방문 전에 어떤 도움을 받을지 살펴보는 상황’을 나누어 본다. 상황에 맞는 입력을 제공하되 버튼·예시를 지정하지 않는다. 같은 참여자의 두 번째 과업은 첫 진입 자료로 합산하지 않는다. 첫 자발 행동을 먼저 관찰하고 이해 질문은 뒤에 묻는다. 중간 질문·도움을 줬다면 개입으로 기록한다.

| 확인 항목 | 관찰·질문과 기록 | 연결 |
| --- | --- | --- |
| 도움 이해 | 어떤 궁금증을 해결할 앱으로 이해했는가? 실제 지원과 다른 기대도 기록 | US-01 AC-01 |
| 행동 발견 | 처음 누른 것·망설인 곳·자력/도움 여부. 시작 화면을 본 시점부터 첫 행동까지 시간 | US-01 AC-02 |
| 예상 결과 일치 | 누른 뒤 기대한 결과와 실제 결과를 비교. 예시를 실제 인식으로 오해했는지 확인 | US-01 AC-02·03 |
| 궁금증 해소 | 이름만 확인했는지, 원래 궁금한 용도·의미까지 해결됐는지, 정확한 설명에 도달했는지 | US-01 AC-03·US-08 |
| 탐색 지속·복구 | 다음에 무엇을 할지와 그 경로를 찾는지. 원하는 관람으로 돌아가는 것도 유효하며 추가 탭을 강요하지 않음 | US-01 AC-03·US-10 |

간단한 기록은 기기·버전·상황, 첫 행동, 도움/막힘, 예상과 실제 결과 차이, 해결/부분 해결/미해결, 다음 행동과 이유로 남긴다. 이는 관찰 기록 항목이며 앱에 자동 행동 추적·개인별 저장을 추가한다는 뜻이 아니다. 예시와 실제 입력 결과는 별도로 집계하고, 실제 인식 흐름은 모델 연결 후 확인한다. 소수 관찰은 사례 분석이며 유의한 효과·재사용 증가를 주장하지 않는다.

기존 무료 AI·검색과 비교할 때는 같은 궁금증을 해결하는 과업으로 평가하고 첫 접속·입력·추가 질문부터 올바른 설명 도달까지의 수고를 포함한다. 오류·포기·실패한 과제도 남긴다. 질문 수가 적어도 해소하지 못하면 개선으로 보지 않는다. 도구·입력·과업 순서·기준선과 최소 개선 기준은 본 평가 전에 정한다. 현재 백로그의 목표 수치를 바꾸거나 새 통과율을 임의로 만들지 않는다. 관찰 후 막힌 원인에 따라 배치·이름·결과 콘텐츠를 수정하며 안내 문구 추가를 기본 처방으로 삼지 않는다.

## 사용자 가치 비교 검증

[제품 원칙](PRODUCT.md#개발-핵심-원칙-사용자가-선택할-이유)의 검증에서는 기능 동작·인식 성능과 사용자 가치를 구분한다. 기능 AC와 공통 DoD 충족은 구현 완료의 근거이며, 기존 방식보다 유용하다는 근거는 별도로 확보한다. 사용자 비교가 해당 작업의 필수 완료 조건이면 이를 수행해야 완료로 판단한다.

- **비교 대상과 과업:** 실제 대상 사용자가 선택할 만한 앱·상용 AI·검색·현장 안내 중 관련 대상을 정하고 같은 목적의 과업을 수행한다. 비교 도구의 확인일·버전 또는 사용 모드·입력·추가 질문·지원 조건을 기록하고 충분한 사용 기회를 준다. 우리 서비스에 유리한 성공 사례만 고르지 않으며 기존 방식으로 충분한 경우도 포함한다.
- **사용자 관점의 지표:** 과업에 맞춰 원하는 설명에 정확히 도달했는지, 질문·조작에 든 수고, 설명 이해, 관심 대상의 발견, 다시 선택할 의향과 이유 등을 고른다. 선호 응답과 실제 선택·재사용 행동은 구분한다. 시간은 성공 여부와 함께 해석하고 실패·포기·잘못된 설명도 기록한다. 모델 정확도만으로 사용자 가치를 주장하지 않는다.
- **사용할 만한 최소 개선 기준:** 사전 관찰·인터뷰·기준선 측정을 바탕으로 지표별 목표 차이와 설정 이유를 본 평가 전에 정한다. 점수 척도와 판정 방식을 명시하며 임의 점수나 결과를 본 뒤 정한 기준을 사전 목표처럼 제시하지 않는다. 목표를 바꾸면 이유를 남기고 후속 평가에서 확인한다.
- **증거와 한계:** 참여자 수·대상 특성, 기기·자료·수행 순서와 학습 효과, 진행자 개입, 결과 분포와 예외를 기록한다. 준비된 답변의 프로토타입과 실제 AI 동작, 모의 과업과 현장 사용을 구분하고 관찰 범위를 넘는 효과를 주장하지 않는다.
- **판단:** 개선이 확인되지 않거나 기존 방식이 더 나으면 반대 근거도 기록한다. 결과에 따라 유지·개선·축소·보류를 검토하며, 미검증 상태를 성공이나 실패로 단정하지 않는다.

관련 작업에는 아래 항목을 짧게 남긴다. 실험 계획·결과가 이미 있으면 링크로 연결한다.

```text
사용자 상황 / 기존 대안:
기대하는 추가 가치:
측정 지표 / 최소 개선 기준과 설정 근거:
확인된 증거 / 미검증 사항:
판단 / 다음 확인:
```

### 발견과 정보 부담의 비교 관찰

[가치 가설](PRODUCT.md#가치-가설-질문을-몰라도-볼거리를-발견하기)을 검증하는 작업에서 적용한다. 아래는 관찰 계획이며 실행 결과나 새 통과 기준이 아니다.

- 먼저 건물 한 곳의 검수 자료로 작은 탐색 실험을 계획한다. 같은 관람 목적·허용 시간에서 기존 검색·상용 AI와 비교하되 ‘관람 포인트를 눌러보라’고 행동을 유도하지 않는다. 비슷한 대상의 순서를 교차하거나 참여자를 나누어 앞서 배운 내용을 다시 발견한 것으로 집계하지 않는다.
- 자연스럽게 작성한 질문과 후속 질문을 허용하고, 입력·사용 모드·요금제·사용일·도움 여부를 기록한다. 프롬프트를 개선한 AI 비교는 별도 조건으로 둘 수 있다. AI에 일부러 빈약한 질문만 제공해 우위를 만들지 않으며 한 번의 출력으로 AI의 한계를 일반화하지 않는다.
- 새롭게 발견한 내용과 그 의미를 자신의 말로 설명하는지, 실제 건물을 다시 살펴보는지, 다음 대상에서 자발적으로 기능을 선택하는지와 이유를 기록한다. 재미·유용함에 대한 말, 탭 수, 다음 대상에서의 행동, 이후 실제 재사용은 각각 구분한다. 모의 사진 관찰을 현장 재관찰로 기록하지 않는다.
- 동시에 읽기 부담, 관심 없는 안내, 기본 정보 찾기의 방해, 건너뛰기·닫기·포기와 이유를 기록한다. ‘건너뜀’ 자체를 실패로 보거나 오래 머문 것을 흥미의 증거로 단정하지 않는다. 설명의 사실 정확성·대상 일치는 별도로 확인한다.
- 소규모 관찰은 아이디어를 고르고 본 평가 기준을 정하는 근거다. 사용할 만한 차이의 기준은 본 평가 전에 정하며, 기존 30% 시간 단축 목표를 이 발견 가설의 입증이나 상용 AI 대비 보장으로 사용하지 않는다. 백로그 목표를 바꾸려면 근거와 사용자 결정을 별도로 남긴다.

## 반복 가능한 평가

새 기능·모델·주요 구조의 구현 전에 평가 계획을 정하고, 관련 변경의 완료 검증에서 같은 조건으로 비교한다. 개발 AI의 작업 성과(요구 충족, 회귀 오류, 재작업, 성공한 작업당 비용·시간)와 제품의 사용자 가치는 따로 평가한다. 자동 점수만으로 제품 가치나 사람의 만족을 입증하지 않는다.

| 평가할 것 | 판정 방법 |
| --- | --- |
| 반드시 지켜야 할 조건 | 코드로 자동 판정한다. 데이터 계약·상태·정확한 계산 등 필수 조건의 실패는 평균 품질 점수로 상쇄하지 않는다. |
| 정답이 하나가 아닌 품질 | 항목별 척도와 부족·보통·우수 사례, 판정 근거를 정한다. 필요한 경우 LLM 채점과 사람의 표본 확인을 조합한다. |
| 사용자가 얻는 가치 | 위 사용자 가치 비교 검증에 따라 같은 과업의 결과와 관찰을 비교한다. |

평가 계획과 결과는 기존 실험·작업 기록에 두고 다음을 포함한다.

- **평가 계약:** 기준선, 대표·실패·경계 사례, 채점 기준과 버전, 필수 실패 조건, 통과 기준과 설정 근거를 본 평가 전에 정한다. 개발용 사례와 최종 확인용 사례를 구분하고, 최종 사례를 개선에 사용했다면 새 확인용 사례를 확보한다.
- **비교 조건:** 입력·자료 버전, 코드 커밋, 실행 환경, 모델·프롬프트·설정·도구 버전(사용한 경우), 실행 명령과 결과 위치를 기록한다. 외부 서비스 등 고정할 수 없는 조건은 실행일과 제약을 남긴다.
- **확률적 결과:** 반복 횟수와 집계 방법을 사전에 정하고 사례별 결과·실패 수·변동을 함께 보고한다. 같은 설정이 같은 출력을 보장한다고 가정하지 않으며, 결과가 불안정하거나 표본이 부족하면 판정을 보류한다.
- **채점 신뢰성:** LLM 채점은 제품 담당자가 정한 예시 판정과 대조해 보정한다. 불일치·중요 오류는 사람이 확인하고, 출력 속 지시문이 채점 규칙을 바꾸지 않도록 평가 입력을 데이터로 취급한다. 채점 모델·기준 변경 시 기준선도 다시 평가한다.
- **실패와 변경:** 평가 실행 오류·누락은 품질 통과가 아니다. 결과를 본 뒤 기준을 바꾸면 이유와 새 버전을 기록하고 후속 평가에서 확인한다. 이미 정한 통과 기준을 낮춰 이전 실패를 통과로 바꾸지 않는다.

평가 사례와 판정기가 준비되면 실행·채점·기준선 비교·결과 저장을 하나의 재실행 가능한 명령으로 묶고 관련 CI에 연결한다. 빠른 결정론적 검사는 관련 PR에서, 비용이 큰 모델 평가는 모델·프롬프트·관련 로직 변경 및 출시 전 등 작업에 맞는 실행 조건을 정한다. 실행하지 않은 평가는 미실행으로 남기고 필수 평가가 남으면 완료·병합 가능으로 판정하지 않는다.

현재 이 절은 운영 규칙이며 새 평가 실행기를 제공하지 않는다. 실제 명령과 결과가 없는 항목은 계획으로 표시한다. 평가 내용의 타당성은 사람의 검토가 필요하며, 자동 병합 차단은 해당 CI와 저장소 보호 설정이 갖춰졌을 때만 주장한다.

## 작업 기록 형식

PR 또는 완료 보고에 다음을 남긴다.

```text
대상: Issue URL 또는 작업 요청
확인한 버전/범위: 커밋 또는 미커밋 변경 목록
환경: 자동 검사 환경 / 수동 기기·OS·브라우저
검사: 명령 또는 재현 단계
기대 결과 / 실제 결과:
판정: 통과 / 실패 / 미실행
증거: 필요한 출력·스크린샷·링크
남은 제한 / 후속 작업:
```

문서만 바꾸는 작업은 로컬 링크, 경로, 상충하는 지침, 변경 범위를 확인한다. 비밀정보·개인정보·원본 제출 자료는 증거에 포함하지 않는다.

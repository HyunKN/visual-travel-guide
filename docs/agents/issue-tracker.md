# Issue tracker 설정

기능 명세와 작업은 [Visual Travel Guide GitHub Issues](https://github.com/HyunKN/visual-travel-guide/issues)에서 관리한다. 발행·분할·통합, 테스트 발견 사항 정리, 다음 작업 선택 전에 읽는다. `to-spec`, `to-tickets`에도 아래 생성 기준을 적용한다.

## 발견 사항을 작업으로 정리하기

발견한 문제와 실행하기로 한 작업을 구분한다. 기록할 가치가 있다는 이유만으로 새 Issue를 만들지 않는다.

1. 관련 상위 Issue와 열린 작업을 확인하고, 필요하면 닫힌 관련 Issue도 검색한다. 같은 목적·완료 기준의 기존 작업을 먼저 찾는다.
2. 아래 표로 기록 위치를 정한다. 테스트 발견 사항은 한 회차의 결과로 모아 정리하고, 항목마다 Issue를 발행하지 않는다.
3. 기존 작업에 포함할 수 있으면 본문의 범위·체크리스트·인수 조건을 갱신하고 변경 이유를 남긴다. 현재 요청 범위 안의 수정은 그 작업에서 해결한다. 새 범위·우선순위 결정은 사용자에게 필요한 선택만 모아서 제시한다.
4. 발행이 필요한 경우에만 목적·완료 기준·독립 추적 이유·관련 기존 Issue를 명시하고, 이미 허용된 발행 범위에서 생성한다. 여러 개를 발행하기 전에는 기존 Issue로 흡수할 항목을 먼저 대조한다.

| 발견한 내용 | 기록·처리 위치 |
| --- | --- |
| 현재 작업의 버그, 빠진 완료 조건, 재검사 | 현재 Issue의 체크리스트와 PR 검증 기록 |
| 아직 끝나지 않은 같은 기능의 보완 | 기존 Issue의 범위·인수 조건 갱신. 기준 변경을 기록하고 이전 검사 결과와 구분 |
| 관찰 사실, 원인이 불명확한 현상, 개선 아이디어 | 관련 Issue의 한 회차 관찰 결과에 모음. 사실·가설·제안을 구분하고 필요한 재현·판단을 표시 |
| 별도 목적·완료 기준이 있고 독립 일정·담당·완료 추적이 필요한 작업 | 기존 작업과 중복되지 않는 새 Issue 후보 |
| 완료된 기능에서 새로 재현된 회귀나 별도 장애 | 이전 Issue·발생 버전·재현 근거를 연결한 새 버그 Issue 후보 |
| 중복·대체된 작업 | 유지할 Issue에 필요한 조건·증거를 옮기고 연결한 뒤 중복·대체 사유로 닫음 |

파일·화면·함수·테스트 케이스마다 Issue를 나누지 않는다. 한 Issue 내부의 구현 단계는 체크리스트로 표현한다. 반대로 목적·담당·배포 시점이 다른 작업을 Issue 수만 줄이려고 한 항목에 계속 붙이지 않는다. 완료된 Issue를 무관한 후속 작업의 통으로 재사용하지 않는다.

## 사람이 다음 할 일을 보는 곳

각 기능의 상위 Issue 본문 맨 위에 `지금 할 일` 요약을 유지한다. 이 프로젝트의 프로토타입 입구는 [상위 Issue #4](https://github.com/HyunKN/visual-travel-guide/issues/4)다. 개별 Issue는 상세 명세와 증거이며, 모두 열어야 순서를 알 수 있는 구조를 만들지 않는다.

```text
목표: 이번에 얻으려는 결과
지금: 실행할 작업 링크 + 다음 행동 + 담당 채팅/사람
다음: 선행 조건이 충족되면 할 작업 링크를 순서대로
막힘 / 사용자 결정: 막힌 이유 + 필요한 행동과 담당. 없으면 없음
대기 후보: 아직 실행을 결정하지 않은 관찰·제안의 기록 링크
갱신 기준: 확인 시점 + 해당하는 커밋/PR 또는 미커밋 범위
```

- 소규모 작업의 기본값은 `지금` 1개, `다음` 최대 3개다. 이는 집중을 위한 운영 기본값이며 전체 Issue 수의 상한이 아니다. 실제로 독립 병렬 작업을 맡긴 경우에는 담당과 변경 범위를 나눠 표시한다.
- 담당 작업 채팅이 착수·인계·완료·새 장애 시 요약을 갱신한다. 같은 상위 Issue를 여러 채팅이 쓰면 갱신 담당을 하나 정하고 최신 본문을 확인해 다른 변경을 보존한다. 사람의 선택이 필요한 경우 AI가 우선순위를 확정하지 않고 추천과 결정 지점을 표시한다.
- 작업 상태와 상세 증거는 해당 Issue/PR에 두고, 상위 요약은 실행 순서와 링크만 유지한다. Wiki·문서·별도 TODO에 진행표를 복제하지 않는다. 추후 GitHub Projects를 쓰면 같은 Issue의 필드·필터로 보여주고 상태를 수동 복제하지 않는다.
- 작업 시작·완료 때 관련 후보를 `기존 작업에 반영 / 별도 작업으로 채택 / 조건부 보류 / 중복·하지 않음`으로 정리한다. 보류에는 다시 볼 조건을 남기고 끝없이 미분류 항목을 쌓지 않는다.
- 통합 종료와 구현 완료를 구분한다. 이동한 인수 조건과 미완료 작업이 유지할 Issue에 실제로 남았는지 확인한다. 다음 행동을 안내할 때는 닫힌 이전 번호 대신 현재 담당 Issue를 연결한다.

## 도구와 연결

- **기존 Issue 보완을 우선한다.** 범위·화면·자료·인수 조건이 추가되면 해당 기존 Issue를 수정한다. 설계 문서의 세부 단계나 수정 때마다 새 Issue를 만들지 않는다. 새 Issue는 기존 과업과 목적·완료 기준이 분리되고 독립 추적이 필요한 경우에만 만든다.
- 기능 전체는 상위 Issue에서 관리한다. 별도 Issue가 필요한 독립 작업만 하위로 연결한다. 지원 도구에 하위 Issue 기능이 없으면 양쪽에 전체 URL 링크를 남긴다.
- 이미 중복 분할한 Issue는 명세·미완료 조건을 기존 Issue로 옮기고 양쪽에 통합 위치를 남긴 뒤 종료한다. 통합 종료를 구현 완료나 요구사항 취소로 표현하지 않는다. 진행 이력을 삭제하지 않는다.
- 선행 작업과 완료 기준을 각 작업에 기록한다. 도구가 의존 관계를 지원하지 않으면 본문에 선행 Issue URL과 상태를 연결한다.
- 실제 발행 전 최신 Issue와 사용 가능한 GitHub connector 또는 `gh` 권한·기능을 확인한다. 도구 지원과 인증 상태를 가정하지 않는다.
- 스킬이 tracker 발행을 요구하면 GitHub Issue 발행을 뜻한다. 사용자가 해당 발행까지 요청한 범위에서 진행한다. AI Workflow 설정은 [Issue #1](https://github.com/HyunKN/visual-travel-guide/issues/1)에서 추적한다.
- 라벨 매핑과 자동 triage는 아직 설정하지 않았다. 이를 요구하는 스킬을 처음 실행할 때 기존 라벨을 조회해 프로젝트 매핑을 정한다. `ready-for-agent` 등 기본값이 서버에 존재한다고 가정하지 않는다.
- PR은 변경과 검증의 기록이다. 외부 PR을 요청 접수·triage 대상으로 삼는 설정은 꺼져 있다.

Issue에는 목적·범위·인수 조건·검증 방법·선행 작업·관련 문서 링크를 담는다. PR 작성에는 저장소의 [PR 양식](../../.github/pull_request_template.md)을 사용한다. 실제로 생성되지 않은 Issue·PR 번호를 문서에 넣지 않는다.

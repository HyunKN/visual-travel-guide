# Sprint 1 개발 착수 검토

확인일: 2026-11-01. 목적은 최신 제출용 계획을 실제 개발의 시작 조건으로 옮기는 것이다. 제품 구현·성능·사용자 효과의 완료 기록은 아니다. 기존 문서의 게시 작업이 다른 채팅에서 진행 중이므로 이 기록은 그 파일을 덮어쓰지 않는다.

## 적용 기준

「PPT 구성 이어가기」의 최신 50개 turn을 읽고 최종 제출용 Planning 11차·Sprint Backlog 6차의 목표·선택 목록·Task·AC를 직접 대조했다. 이번 검토는 내용·기술 준비 검토이며 Word 페이지 배치 재검수가 아니다. 개인 정보가 있는 원본 Word는 공개하지 않는다.

- 프로젝트명: 관광객을 위한 장소 탐색 가이드 서비스 / Visual Travel Guide. 11/1 후속 확인에서 사용자가 수정한 공개 Planning의 명칭을 적용했다.
- Sprint: 10/26~11/16. 개발은 11/15까지, 11/16 Review·시연.
- 목표: 지원 장소 알아보기 → 자기 시선 기록 → 같은 장소의 다른 사람 흔적 만나기 → 관심에 따라 관람 이어가기.
- 첫 적용 장소: 근정전·교태전·광화문 3곳. 제품 전체를 경복궁으로 한정한 것은 아니다.
- 선택 Story: US-01·04·05·08·07·09·10·17·13·14·15·16, 12개·50 SP. 전체 Product Backlog는 17개·70 SP.
- US-02 이름 검색·US-03 지도/구역 탐색·US-06 후보 비교는 Sprint 2. US-17의 현재 위치·주변 지원 장소 2D 지도는 Sprint 1에 포함한다.
- US-11·12는 후순위. 직접 장소 선택은 현재 흐름의 대체 경로이며 US-02/03 전체 완료를 뜻하지 않는다.
- 사용자 사진 위에 같은 장소의 흔적 표시 → 누르면 50자 이내 글 펼침 → 닫으면 사진 복귀. 특정 창문·기둥에 고정하거나 포스트잇 모양으로 디자인하는 요구가 아니다.
- 자기 기록은 비공개 로컬 저장. 공개에 동의한 장소·짧은 텍스트만 공유한다. 사진 공개 업로드는 제외한다.
- 기본 설명·사진 탐색은 기록 전에도 사용한다. 타인의 글 열람 순서와 내 글 공개 동의는 별개다.
- 기술 선정: MobileCLIP2-S3·ONNX Runtime·Supabase. React Native + Expo 시작 방향과 네이티브 연결의 검증은 별개다. 구현할 때 버전 호환을 다시 확인한다.
- 먼저 PC Android Emulator에서 실행, 11/8까지 실제 Android 기기 1대 이상 사전 확인. 11/12 범위 고정, 11/13~15 최소 2명 비교 관찰·수정·시연 준비.

기존 [10/29 조정안](sprint1-scope-replan.md)의 66시간·이름 검색 앞당김·미선정 모델/공유 서비스는 현재 착수 기준으로 사용하지 않는다. 최신 선택 목록은 [Product Backlog](../PRODUCT_BACKLOG_DRAFT.md)와 대조한다. Word 양식 원문·안내 규칙·제출 체크는 이 준비 작업으로 수정하지 않는다.

## 모델 계약과 T04의 첫 확인

모델 수신 위치는 저장소 루트의 `local-assets/models/mobileclip2-s3/bundle/`로 준비했다. 노트북에도 같은 구조를 사용하고 같은 export의 ONNX·external data·metadata를 함께 보관한다. `local-assets/` 전체는 Git에서 제외하며, 다른 기기로 자동 동기화되는 폴더가 아니다. 원본 확보 후 파일 해시·모델 계약을 확인하고, 배포용으로 가공할 때 원본을 덮어쓰지 않는다. 현재 이 폴더는 비어 있으며 모델 확보를 뜻하지 않는다.

현재 확보한 metadata의 내용은 다음과 같다. 실제 ONNX를 읽어 shape·dtype·연산 지원·파일 크기·해시를 검증하기 전까지 모델 동작을 확정하지 않는다.

| 항목 | metadata / 코드에서 확인한 값 | 후속 확인 |
| --- | --- | --- |
| 모델 | MobileCLIP2-S3, fp16 weight storage / fp32 compute 정책 | 정확한 원본 export, 모델·external data 쌍과 사용 조건 |
| 이미지 인코더 | image 입력, embedding 출력. image_size 224, embedding_dim 512 | 실제 shape/dtype, metadata와 바이너리 일치 |
| 전처리 | float32 NCHW, RGB별 mean/std 정의 | EXIF 방향·색상·보간·크롭·정규화 parity |
| 기존 앱 구현 | short-side scale 기본값 1.15, cubic resize 후 center crop | preprocessing.json에는 scale/보간이 없음. 과거 앱 코드를 학습/평가 정답으로 단정하지 않음 |
| 등록 벡터 | prototype_index의 embedding 사용 | 차원·정규화·클래스 ID·장소 ID 일치 및 교태전 등록 |
| 확정/보류 | 이전 confidence policy 파일 존재 | 이번 3곳에 검증된 임곗값이 아님. 기준 설정용 데이터로 정책을 먼저 기록 |

이번에는 이름 검색이 후순위이므로 이미지 인식에 필요한 인코더와 벡터부터 확인한다. 텍스트 인코더를 자동으로 전부 번들에 넣지 않는다. ONNX external data를 분리한 채 두 파일의 상대 경로를 유지하고 네이티브에서 적재 가능한지 확인한다. fp16이라는 이름을 입력 텐서가 float16이라는 뜻으로 해석하지 않는다.

등록 사진, 판단 규칙 설정용 사진, 독립 평가 사진을 분리하고 같은 원본의 크롭·증강본이 다른 세트로 새지 않게 묶는다. 범위 밖·흐림·일부만 보이는 사진을 포함한다. 세트·정답·판정 기준은 실행 전에 확정하고, 교태전 및 전체/건물별 Top-1·Top-3·오확정·보류와 위치 사용 여부를 기록한다. 기존 23개 클래스 결과를 새 3곳의 성능으로 전용하지 않는다.

## 실제 착수 세부 계획 — 11/1 후속 합의용

이 절은 기존 Task의 실행 분해다. 새 Story·Task 번호나 별도 진행판을 만들지 않는다. 현재 상태·잔여 시간·실행 증거는 기존 Issue/PR에서 관리하며 아래 완료 조건은 앞으로 확인할 항목이다. 후속 확인에서 [공개 Planning](https://github.com/HyunKN/visual-travel-guide/blob/main/docs/sprints/SPRINT1_PLANNING.md)의 목표·선택 목록·의존 순서를 대조했다. GitHub Issue 실시간 조회는 CLI 인증 오류(HTTP 401)로 확인하지 못했으므로 이 기록을 원격 Issue 갱신으로 간주하지 않는다.

### 1. 첫 작업 묶음: 설치해서 켜지는 Android 앱 (T17 일부 → T02)

목표는 화면 디자인 완성이 아니라 같은 소스로 다시 빌드하고 설치할 수 있는 앱이다.

1. 구현 직전 기준 브랜치·원격 변경과 공유 중인 미커밋 파일을 확인한다. 이번 앱의 작업 경로는 `mobile/`을 제안하며 기존 `prototype/`은 유지한다. 관련 기능 Issue가 있으면 그 범위 안에서 진행한다.
2. 최소 계약을 먼저 적는다: 장소 ID, 사진의 임시/영구 경로, 인식 요청 ID와 결과 상태, 개인 기록 ID, 공개 글 ID. 사진 취소·재선택 시 오래된 결과를 버리는 규칙을 포함한다.
3. 설치 공간·가상화·기존 SDK/Java 경로를 확인한다. 실제 제공되는 Expo/React Native/ONNX Runtime 조합과 필요한 JDK/SDK를 공식 자료로 재확인한다. 기존 전역 Java를 제거하지 않고 프로젝트의 빌드 환경을 선택한다.
4. SDK·시스템 이미지·AVD를 준비하고 TypeScript + React Native + Expo Development Build 최소 앱을 생성한다. Expo Go 실행을 네이티브 모델 연결 검증으로 대체하지 않는다.
5. 첫 화면과 돌아갈 수 있는 임시 상세 화면만 연결한다. Android 시스템 뒤로가기, 앱 종료·재실행을 확인한다. 이때 임시 화면을 최종 UI 또는 US-01 완료로 표시하지 않는다.
6. 의존성 lockfile·실제 버전·실행 명령·AVD/ABI를 남기고 다시 빌드→설치→실행한다.

**종료 증거:** 에뮬레이터에서 앱 실행, 재현 가능한 빌드 명령과 로그, 설치된 앱/빌드 식별, 뒤로가기·재실행 결과. SDK 설치만 끝난 상태는 T02 완료가 아니다.

### 2. 모델을 실제로 부르는 작은 실험 (T04 일부, 이후 T05·T22)

사용자 준비: 노트북의 같은 export에서 ONNX·external data·metadata를 `local-assets/models/mobileclip2-s3/bundle/`로 전달한다. 전달 전에도 1번과 아래 콘텐츠 작업을 진행할 수 있다.

1. 원본 파일명·상대 경로·크기·SHA-256·사용 조건을 확인하고 별도 검증용 사본을 사용한다. Git에는 바이너리를 올리지 않는다.
2. 실제 ONNX 입력/출력 이름·shape·dtype와 metadata를 대조한다. 참조 실행 환경에서 한 장을 전처리해 출력 shape·유한값·벡터 norm을 확인한다.
3. Android에서 두 모델 파일을 읽을 수 있는 경로로 배치하고 세션 생성→동일 입력 텐서 추론을 확인한다. 첫 로드와 반복 추론 시간을 구분해 기록한다. 전체 이미지 전처리를 연결하기 전에 동일 텐서 출력으로 런타임 차이를 좁힌다.
4. EXIF·회전·리사이즈·크롭·정규화를 연결하고 참조 전처리 및 출력과 비교한다. 출력 오차 허용값은 dtype·참조 결과를 근거로 비교 전에 기록한다.

### 3. 공유가 실제로 되고, 남의 글은 바꾸지 못하는지 확인 (T15 + T16·T21 일부)

5. 신고와 관리자 숨김을 연결하고 관리자 권한을 앱에서 분리한다. 통신 실패 시 개인 기록은 남고 재시도가 중복 글을 만들지 않아야 한다.

**종료 증거:** 두 세션의 실제 저장·조회·거부 결과. 프로젝트가 준비되지 않으면 스키마·정책·실행할 검사만 준비하고 실제 연동은 미실행으로 둔다. 로컬 가짜 글로 실제 사용자 공유를 검증했다고 보고하지 않는다.

### 5. 작업을 마치는 기준과 당장 한 세션의 범위

- **첫 개발 세션:** 최소 데이터 계약 → 환경/버전 확인 → 앱 생성·에뮬레이터 실행. 3~5시간은 작업 예산이며 성공 보장이 아니다. 설치가 오래 걸리면 다운로드 대기와 실제 작업 시간을 나누고 오류 원인·다음 행동을 남긴다.
- **다음 묶음:** 확보된 모델의 첫 Android 호출과 Supabase A/B 검사. 초기 T04 2시간을 자료 확보·전처리·독립 평가 전체 완료의 보장으로 보지 않는다. 예산을 넘기면 원인과 실제 남은 작업을 재추정한다.
- **기능마다:** 관련 AC와 오류·복구를 검사하고 증거를 남긴다. T18에서 처음 모든 검사를 시작하지 않는다. 첫 진입 UI와 기록 부담도 최종 비교 이전에 짧게 점검한다.
- **11/8까지:** 실제 Android 기기를 확보하여 설치·사진·모델·권한·저장·복귀를 확인한다. 에뮬레이터 결과를 기기 성능으로 바꾸어 보고하지 않는다.
- **11/12:** 실제 구현과 미해결 위험을 바탕으로 범위를 고정한다. 남은 기능을 자동 삭제하거나 성공 기준을 낮추지 않고 사용자와 우선순위를 판단한다.
- **11/13~15:** 최소 2명 비교 관찰·수정·회귀·APK/실행 방법 정리. 기존 검색/AI와 같은 목적에서 발견·재사용 선택 이유·기록 부담을 비교하며 2명의 긍정 응답을 시장 수요 입증으로 확대하지 않는다.

이번 계획에서 개발자는 구현·검사·잔여 추정을 맡고 사용자는 원본 모델 전달, 실제 기기 확보, 필요 시 Supabase 계정/프로젝트 준비와 제품 선택을 맡는다. 지금 당장 필요한 사용자 준비는 모델 묶음 전달이며 기기와 프로젝트 준비는 해당 작업 전에 확인한다. 추가 설문이나 문서 작성을 개발 착수의 전제 조건으로 늘리지 않는다.

### 6. 11/8 첫 전체 실행본 목표와 조기 수정 계획

11/2 사용자 보충: Sprint·날짜 구간은 현재 위치와 목표를 확인하는 참고이며 해당 날짜까지 작업을 기다리는 순서표가 아니다. 선행 조건이 준비된 작업은 즉시 진행하고, 작게 구현·검증한 실제 흐름을 일찍 사용하며 계속 수정한다. 빠르게 만들기 위해 데이터·저장·권한·인식 평가를 생략한다는 뜻은 아니다. 아래 날짜별 표는 당시 목표로 보존하고 실제 다음 작업은 현재 준비·막힘·실행 증거를 기준으로 정한다.

11/1 사용자 확인: 11/8까지 모델 추가 학습·평가와 기록·공유를 포함한 Sprint 1 전체 흐름을 한 번 동작시키는 목표로 진행한다. 빠른 실행과 피드백 시간을 확보하려는 내부 목표이며, 수업 Sprint 종료일 11/16과 AC·DoD는 유지한다. 첫 실행본을 최종 검증 완료로 간주하지 않는다. 기존 Task 안의 실행 단위로 관리하고 Word 추정값을 소급 변경하지 않는다.

11/4는 첫 기본 흐름과 모델/공유 준비 상태를 점검하는 시점, 11/6은 11/8 통합 실행 가능성을 판단하는 시점으로 둔다. 막힘은 해당 날 해결·대안·잔여를 보고하고 최종 주말까지 숨기지 않는다. 실패 원인을 좁히는 동안 직접 선택·비공개 기록으로 개발은 이어갈 수 있으나 모델·공유의 미완료 상태를 유지한다. 사용자 가치 관찰은 첫 쓸 수 있는 실행본부터 시작하고, 11/13~15의 비교·회귀 기간도 유지한다.

## 시간 검토

최종 제출 문서의 계획 기준은 10/31~11/15 가용 60시간, 20개 Task 추정 합계 47시간(Story 37 + 공통 10), 예비 13시간이다. 40개 AC가 Task에 연결되어 있으나 실행 결과는 미실행이다.

11/1부터 11/15까지 다시 계산하면 평일 10일×3 + 주말 5일×5 = 최대 **55시간**이다. 오늘 시간이 이미 소진됐다면 더 적다. 작업을 하나도 완료하지 않았다고 가정할 때 47시간 대비 단순 차이는 8시간이다. 10/31의 작업을 5시간 소진 또는 5시간 완료로 추정하지 않는다. 이번 준비·원본 파일 확보·SDK 설치 이후 실제 잔여를 다시 추정하며 Word의 역사적 60/47/13 값을 몰래 바꾸지 않는다.

오늘은 계획에 적힌 11/1 기술 판단일이다. 모델 바이너리·Android 실행·Supabase 연결을 모두 성공했다고 보고할 수 없는 상태다. 따라서 47시간이 충분하다는 근거는 아직 없으며, 첫 연결 뒤 실제 잔여와 위험을 사용자에게 보고한다. 미구현 Task를 완료로 체크하거나 계획 SP를 velocity로 기록하지 않는다.

## 이번 준비의 범위

이번에는 최신 계획 읽기·원본 내용 대조·환경 및 모델 metadata 확인과 착수 기준 작성을 수행했다. 제품 패키지 생성, SDK/모델 설치, 앱 빌드·추론·클라우드 연결·사용자 테스트는 수행하지 않았다. 공유 중인 기존 문서·Word·Issue의 상태도 수정하지 않았다. 새 문서의 링크/형식 검사는 수행하되 실행하지 않은 Android 동작을 검증 결과에 넣지 않는다.

# AI와 개발하는 흐름

이 문서는 작업 절차의 원본이다. 작업 시작 시 읽고, 기록 위치나 단계·검증 방식이 바뀔 때 갱신한다. 아래 스킬 이름은 설치된 지침을 선택하는 기준이며 자동 실행 파이프라인이 아니다.

## 한 작업의 시작부터 완료까지

| 단계 | 할 일 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 1. 이해·설계 | 요청·관련 문서를 읽고 아래 구현 전 통과 조건을 정리한다. | 적용 항목의 근거와 필요한 사용자 결정이 확인됨 |
| 2. 명세·분할 | [Issue 운영 규칙](agents/issue-tracker.md)에 따라 기존 작업을 먼저 갱신하고 독립 추적이 필요한 단위만 분리한다. | 기존 작업과 중복되지 않고 완료 기준·선행 작업·관련 문서가 연결됨 |
| 3. 구현 | 한 흐름씩 구현하고 설계가 달라지면 해당 문서도 갱신한다. | 요청한 행동을 확인할 수 있는 변경이 준비됨 |
| 4. 검증·리뷰 | 명세 충족과 코드 규칙을 각각 확인하고 실제 검사 결과를 기록한다. | 실패를 해결하거나 남은 제한·미확인 사항을 명시함 |
| 5. 전달·게시 | PR 또는 완료 보고에 변경·증거·문서 영향을 남긴다. main 병합 후 Wiki 게시 결과를 확인한다. | 수행한 작업과 하지 않은 작업을 구분해 전달함 |
| 6. 학습 | 관찰 결과를 관련 Issue에 모아 기존 작업 반영·별도 채택·보류·하지 않음을 정하고 반복된 문제만 공통 규칙에 반영한다. | 상위 Issue에서 지금 할 일·다음 행동·사람이 결정할 점을 알 수 있음 |

작은 수정은 별도 Issue를 억지로 만들지 않고 사용자 요청을 작업 기준으로 삼을 수 있다. 중요한 제품 선택은 사용자가 결정하며, 승인된 범위 안의 가역적인 구현 선택은 AI가 근거와 함께 진행한다.

## 구현 전 통과 조건

2026-10-22 채택: 사용자가 문제와 성공 기준·주요 설계를 주도하고 AI는 대안 검토·구현·검증을 맡는다. 새 기능, 주요 구조 변경, 모델 도입·교체에서는 아래 항목을 기존 작업 Issue 또는 설계 문서 한 곳에 기록한다. 기록을 위해 새 Issue나 문서를 자동 생성하지 않는다. 이미 합의된 내용은 링크로 재사용한다.

| 조건 | 구현 전에 확인할 근거 |
| --- | --- |
| 문제·원인 | 관찰한 현상과 원인 가설을 구분하고, 영향이 큰 원인 후보와 이를 구분할 검사·확인 결과를 남긴다. 미확인 원인은 가설로 유지한다. |
| 해결 수단 | [구조 선택 기준](ARCHITECTURE.md#구조를-선택할-때)에 따라 규칙으로 처리할 부분, 확률적 추론이 필요한 부분, 아직 조사할 부분을 나눈다. |
| 평가 | [반복 평가 규칙](QUALITY.md#반복-가능한-평가)에 따라 기준선·평가 사례·판정 방법·통과 기준·실행 방법을 구현 전에 정한다. |
| 사용자 설계 | 사용자가 중요하게 보는 상황·차별점·초기 구조와 대안 비교, 선택 이유를 확인한다. 사용자가 AI의 초안 작성을 맡긴 경우에도 제안과 채택을 구분한다. |

원인 분석은 `관찰 → 원인 후보 → 후보를 구분할 검사 → 영향이 큰 원인 확인 → 작은 해결 작업` 순서로 진행한다. 하나의 근본 원인을 억지로 확정하지 않는다. 자료가 부족하면 기능 구현 대신 범위·종료 조건이 있는 조사나 실험부터 수행한다.

주요 설계에서는 AI가 완성안을 먼저 제시하기 전에 기존 기록에서 사용자의 관점을 찾는다. 없으면 사용자에게 짧은 문장·그림으로 먼저 제안할 기회를 주고, 답을 기다리는 동안 사실 조사와 제약 확인을 진행한다. 사용자가 초안 작성을 맡기면 AI가 대안을 준비한다. 제품 방향·핵심 구조·평가 기준의 결정은 사용자가 하며, AI가 이를 임의로 확정하거나 바꾸지 않는다. 이미 승인된 결정과 범위 안의 작은 구현 선택은 재승인 없이 진행한다.

적용 항목이 빠졌거나 필요한 사용자 결정이 남아 있으면 기능 구현으로 넘어가지 않고 다음 확인을 기록한다. 작은 버그 수정·문구·문서 작업은 문제·변경 범위·검증 방법을 짧게 적고 나머지 항목의 비적용 이유를 한 줄 남긴다. 모든 작업에 아키텍처 대안이나 사용자 실험을 요구하지 않는다.

작업 기록은 아래 정도로 유지하고 상세 평가·설계가 있으면 연결한다.

```text
문제·원인: 관찰 / 가설 / 먼저 확인할 원인과 근거
해결 수단: 규칙·코드 / 확률적 추론 / 조사 필요
사용자 관점·설계 결정: 차별점 가설 / 선택·이유 / 결정 근거 링크
평가 계획: 기준선·사례·판정·실행 방법 링크
시작 판정: 구현 가능 / 조사·사용자 결정 필요 / 간소 적용과 이유
```

## 사용자 가치를 되묻는 시점

[제품 원칙](PRODUCT.md#개발-핵심-원칙-사용자가-선택할-이유)을 기능 작업에 다음과 같이 적용한다. 기록은 해당 Issue·PR 또는 완료 보고에 남기며 별도 진행 목록을 만들지 않는다.

| 시점 | 확인하고 남길 내용 |
| --- | --- |
| 기능 선정·설계 시작 | 사용자 상황, 실제 비교 대상, 기대하는 추가 가치, 검증 방법과 사용할 만한 최소 개선 기준. 기준이 미정이면 결정할 방법·시점을 기록 |
| 구현 중 주요 선택 | 선택한 UI·정보 구성·기술이 가치 가설에 어떻게 기여하는지 확인. 가설과 어긋나면 범위와 접근을 재검토 |
| 리뷰·완료 보고 | 기능 동작 결과와 사용자 가치 증거를 따로 보고. 비교를 하지 않았다면 미검증으로 표시하고 다음 확인을 명시 |
| Sprint Review·백로그 재검토 | 기존 방식보다 나아졌다는 근거와 선택할 만큼의 차이가 있는지 재검토하고 유지·개선·축소·보류 결정에 연결 |

기능마다 작은 비교 실험을 반복할 필요는 없다. 관련 기능은 하나의 사용자 과업으로 묶어 평가한다. 문구·문서·개발환경 같은 지원 작업은 연결된 가치 가설이나 간접 기여를 짧게 적고, 새 사용자 실험이 필요하지 않으면 이유를 남긴다.

관람 안내·콘텐츠·화면 작업에서는 [질문을 몰라도 볼거리를 발견하기](PRODUCT.md#가치-가설-질문을-몰라도-볼거리를-발견하기)를 읽고, 시작과 리뷰 때 **‘스스로 질문하지 못했던 무엇을 발견하게 하는가? 정보를 과하게 보여주거나 선택을 강요하지 않는가? 그 가치의 증거와 다음 확인은 무엇인가?’**를 되묻는다. 편리함뿐 아니라 흥미·발견도 살피고, [정보량 원칙](DESIGN.md#발견을-돕는-정보량)과 [비교 관찰](QUALITY.md#발견과-정보-부담의-비교-관찰)을 연결한다. 관련 없는 지원 작업에는 간접 기여 또는 비적용 이유만 남긴다. 이 점검은 자동 알림이나 별도 기능 구현 지시가 아니다.

## 채팅 분리

이번 시나리오 프로토타입의 설계→작업 분할→Sol 인계는 [상세 설계](prototype/README.md), [작업안](prototype/TASKS.md), [인계문](prototype/HANDOFF.md)을 사용한다. 상세 설계는 코드처럼 버전을 관리하고, 수용 범위·진행 상태는 Issue, 구현·검증은 PR로 연결한다. 구현 준비 완료와 사람 관찰 완료를 별도 조건으로 관리한다.

AI Workflow·개발환경 채팅은 공통 규칙·스킬·문서·CI·Wiki 운영을 관리한다. 기능 구현, 프로토타입, 제품 테스트는 프로젝트의 개별 작업 채팅에서 진행한다. 시작 정보와 인계 기준은 [THREADS](THREADS.md)를 따른다. 별도 채팅의 대화 내용이 자동 공유된다고 가정하지 않고 Issue·문서·커밋을 연결한다.

## 문서 갱신 규칙

변경한 영역에 해당하는 문서를 [문서 지도](README.md)에서 찾아 같은 PR에 포함한다. 예를 들어 후보 카드의 선택 상태를 바꾸면 DESIGN, 모듈 간 데이터 전달이 바뀌면 ARCHITECTURE, 완료 판정이 달라지면 QUALITY를 갱신한다.

동작이 그대로인 작은 수정은 문서 변경 없이 그 이유만 기록한다. 테스트 통과 로그를 공통 문서에 누적하지 않고 해당 작업의 PR·Issue에 남긴다. 실행 명령은 실제 스크립트와 환경을 확인한 뒤 프로젝트 README에 연결한다.

지침을 추가·수정할 때는 적용 시점, 바꾸려는 행동, 확인 방법을 명시한다. 같은 의미는 기존 원본을 수정하고 다른 문서·스킬에서는 연결한다. 중복·오래된 내용·행동을 바꾸지 않는 설명은 이 변경과 관련된 범위에서 정리하고, 유효한 사용자 제약을 없애는 변경은 결정 사항으로 드러낸다. 일회성 작업 지시를 공통 규칙으로 누적하지 않는다.

스킬을 사용하기 전에 설치된 `SKILL.md`를 읽고 지원 도구·입출력·권한을 확인한다. 설치되지 않은 환경에서는 이 문서의 절차로 진행하고 사용하지 않은 스킬을 사용했다고 보고하지 않는다. 스킬은 전역 설치에 의존하므로 이 저장소를 복제하는 것만으로 설치되지는 않는다.

`setup-matt-pocock-skills`의 프로젝트 설정 구조를 참고해 [tracker](agents/issue-tracker.md)와 [domain](agents/domain.md)을 연결했다. 설정 작업은 [Issue #1](https://github.com/HyunKN/visual-travel-guide/issues/1)에서 관리한다. 전체 setup 실행과 triage 라벨 설정은 아직 수행하지 않았다.

## 사용자 맞춤 협업 스킬

아래 세 가지는 사용자가 업무 방식을 설계하고 Codex가 작성한 개인 맞춤 스킬이다. Matt Pocock 스킬과 구분하며, 전역 스킬 폴더에 설치해 다른 프로젝트에서도 사용할 수 있다. 이 저장소를 복제하는 것만으로 설치되지는 않는다.

| 호출 이름 | 한국어 표시 이름 | 하는 일 |
| --- | --- | --- |
| `$pr-review-manager` | PR 리뷰·병합 관리 · 사용자 맞춤 | PR마다 별도 채팅에서 검토·수정을 진행하고 상위 채팅이 문제와 병합 순서를 관리한다. |
| `$coordinate` | 병렬 작업 조율 · 사용자 맞춤 | 독립 업무를 여러 하위 에이전트에게 나누고 담당자끼리 협의한 결과를 상위 에이전트가 통합·확인한다. |
| `$manager` | 두 에이전트 공동 작업 · 사용자 맞춤 | 두 에이전트 모두 제작 업무를 맡고, 그중 한 명이 취합한 결과를 상위 에이전트가 확인한다. |

실제 호출 전 설치된 `SKILL.md`를 읽는다. `manager`는 함께 설치된 `coordinate`의 공통 협업 규칙을 사용한다. 담당 파일의 중복 편집을 막고, 범위·소유권 변경과 해결하지 못한 문제를 상위에 보고한다. 발견 사항은 기존 작업 기록에 모으고 [Issue 운영 규칙](agents/issue-tracker.md)에 따라 분리한다.

스킬 선택은 새 채팅 생성·메시지 전송·push·병합 권한을 대신하지 않는다. 사용자가 요청한 범위에서 실행하며, 짧고 순차적인 후속 작업은 전달·검토 비용을 고려해 현재 담당자가 처리한다. 특정 모델을 고정하거나 실제 측정 없이 비용 절감을 주장하지 않는다.

설치 파일 형식·한국어 설명·출처·내부 링크를 확인했다. 실제 병렬 협업과 PR 병합을 끝까지 수행하는 검증은 아직 하지 않았다.

## 스킬을 이 프로젝트에 적용할 때

- 사용자 지시·실행 환경 권한·프로젝트 규칙을 적용한다. 스킬의 commit·게시·위임 지시를 사용자의 새 권한으로 해석하지 않는다.
- TDD는 공개 동작을 관찰할 경계를 명세 단계에서 정하고 필요한 변경에 적용한다. 문서 편집에는 링크·내용 확인처럼 적절한 검사를 사용한다.
- 리뷰 범위를 먼저 기록한다. 커밋 비교뿐 아니라 이번 작업의 미커밋 변경과 새 파일도 검토한다.
- 승인된 작업에서 병렬 협업·PR 조율에 사용할 스킬은 설치했다. 상시 실행·장기 예약 자동화는 구성하지 않았다.

## 현재 자동화 수준

- AGENTS 읽기 지침과 PR 양식: 이 저장소에 정의했다. 실행 결과의 확인은 별도로 필요하다.
- 문서 내용 판단·수정: 작업하는 AI와 사람이 수행한다.
- 문서 검사와 Wiki 게시: [GitHub Actions](../.github/workflows/docs.yml)로 실행한다. 설정 자체와 실행 성공을 구분하며 결과는 [WIKI](WIKI.md)의 확인 절차를 따른다.
- 구현 전 통과 조건과 평가 계획: 문서·PR 리뷰로 확인하는 운영 규칙이다. 이번 반영으로 제품 평가 실행기나 병합 차단 검사가 추가된 것은 아니다. 실제 평가 사례와 명령을 갖춘 작업에서 자동 검사를 연결하고, 병합 강제 여부는 저장소의 필수 검사·보호 설정까지 확인한다.

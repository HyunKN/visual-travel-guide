# 프로토타입 보완 개발 설계 — 후보 확인·다음 탐색·관련 질문

## 2026-10-17 변경 — v0.4 자유 탐색 앱

사용자가 [모바일 UI 배치안](UI_LAYOUT_REVIEW.html)을 검토하고 구현을 요청했다. 하나의 앱에서 홈↔검색↔사진 탐색↔설명을 자유롭게 오간다. 시나리오별 허용 사진·후보·다음 관람 제한은 적용하지 않는다. 시작 preset은 과거 URL·리허설 호환용 시작점만 정하며 필수가 아니다.

- H에 실제 검색 입력, 공통 상단 뒤로/검색과 하단 홈/검색/사진 탐색을 제공한다. 약80:20의 시각 위계로 주 탐색을 앞세우고 호기심 제안은 88px 사진의 작은 행으로 줄인다.
- S 검색은 확보한 대상 이름·설명·질문 안에서 문자열 조회하며, 결과 없음과 사진 탐색 대안을 제공한다. 검색 결과→A→뒤로는 검색어·결과·위치·포커스를 복원한다.
- N은 모든6장면을 제공한다. C04에 연결된 후보 확인은 어느 출발 시나리오에서도 접근할 수 있다. case/option/참고 장면·답변 검증은 유지한다.
- 다음 관람 관계는 검수된 연결이 있으면 어느 출발 시나리오에서도 사용한다. S5 전용 기능이 아니다.
- 시나리오는 과제와 순서를 정하는 관찰 문서에 둔다. 앞서 본 대상이 있으면 학습·사전 노출로 기록한다. 앱을 잠가서 최초 발견을 인위적으로 보장하지 않는다.

이 변경은 아래 v0.3의 preset 잠금·N 최대3장·S4/S5 전용 진입 규칙을 대체한다. 나머지 검수·실패 복구·준비된 답변 원칙은 유지한다. 실제 촬영·인식·GPS·LLM은 구현하지 않는다.

설계 버전: 0.3 · 2026-10-16. **v2 계약·실제 자료·후보 C·N·홈/이력·질문 지원 한계·다음 관람을 구현했다.** 통합 콘텐츠는 `2026-10-16-scenes.3`이다. 실제 검사·실기기 미실행은 [검증 기록](../../prototype/VERIFICATION.md), 진행은 기존 P Issue, 관찰은 [실행 안내](OBSERVATION_RUNBOOK.md)를 따른다. 설계 문서 자체를 새 범위·발행·배포 승인으로 해석하지 않는다.

후속 기록: 사용자의 이슈 증가 방지 요청에 따라 [기존 P 이슈](TASKS.md)에 통합하고 R 이슈 6개는 통합 종료했다. R01~R06은 문서 내부 단계다. 기본 앱·설계·P01은 `7e8e748`로 푸시했으며 P02 보완의 실제 버전·검사는 [해당 Issue](https://github.com/HyunKN/visual-travel-guide/issues/7)에 남긴다.

## 1. 목적과 이번 결정

준비된 사진에서 궁금한 대상을 확인하고 설명을 읽은 사람이 선택을 고치거나 다른 탐색으로 이어갈 수 있는지 관찰한다. 전체 서비스의 검색·인식 기능을 완성하는 단계가 아니다. 이번 관찰은 Product Backlog와 User Story를 구체화하는 근거이며 Sprint 0의 기술 검증과 구분한다.

| 요청 | 개발 설계 결정 | 확인할 사용자 행동 |
| --- | --- | --- |
| AI가 후보를 찾은 뒤처럼 경험하기 | 특정 테스트 상황에서만 준비된 건물 후보 2개를 제시 | 입력 사진과 구별 단서를 대조하고 확인·보류·수정 |
| 설명 다음 행동이 막히지 않기 | 같은 사진의 다른 부분 / 새로운 대상 / 고정된 다음 관람 제안을 구분 | 의도에 맞는 경로를 찾고 이전 설명으로도 복귀 |
| 준비된 질문 방식 구체화 | 기본 설명 먼저, 선택적 관련 질문, 없는 질문은 지원 한계로 처리 | 설명의 충분성, 추가 질문 발견, 미지원에서 복귀 |

실제 AI·GPS·카메라·파일 업로드·이름 검색·지도·추천 알고리즘·LLM·자유 입력·진행자 응답 큐·서버·DB는 추가하지 않는다. 기존 방식 대비 시간 단축과 사진+위치 PoC는 이번 관찰의 완료 조건이 아니다. 홈/3D/유리 재질 재설계도 포함하지 않는다.

## 3. 사용자 흐름과 화면

```text
일반 상황: H → V(전체/부분 지정) → A(기본 설명) → Q → A(질문 답변)
비교 상황: H → V(준비 사진 확인) → C(후보 2개) → A(선택 후보 설명)
                                   └ 해당 없음 → E → C 또는 입력 사진 V
설명 이후: A → 같은 사진의 다른 부분 V
           A → 다른 대상 알아보기 N → 준비된 다른 장면 V
           A → 다음 관람 제안 → 다른 대상 A
```

H의 주요 행동 하나와 홈 호기심 카드 최대 하나는 유지한다. 일반 흐름에 매번 C를 끼우지 않는다. 후보 비교 상황은 별도 S4 preset으로 지정하며 사용 중 무작위로 발생시키지 않는다.

### 3.1 C — 준비된 건물 후보 확인

- 테스트 시작 안내: `사진 인식과 위치 확인 없이, 준비된 결과로 사용 흐름을 체험합니다.` 제품 화면에서도 기존 프로토타입 안내를 유지한다.
- S4의 V는 검수한 입력 사진과 `이 사진으로 알아보기`를 표시한다. 이 상황에서는 부분 지정과 `건물 전체 알아보기` 대신 이 행동 하나를 쓴다. 가짜 카메라 권한·분석 지연·진행률은 없다.
- C 제목: `어느 건물과 닮았나요?` 보조 문구: `사진과 아래 특징을 비교해 보세요.`
- 상단에 입력 사진을 유지한다. 후보의 참고 사진과 각각 `알아보는 사진` / `비교용 사진`으로 구분한다. 사진 확대는 기존 동작을 재사용한다.
- 후보 2개를 세로로 배치한다. 각 후보는 사진, 공식 이름, 구별 단서 1~2개, `이 건물이에요` 버튼을 갖는다. 확률·추천 순위·정답 강조는 없다.
- 첫 후보를 자동 선택하지 않는다. 같은 사진에서 확인할 수 없는 역사·용도만으로 구별하라고 요구하지 않는다. 후보 사진의 크기·정보량은 비슷하게 맞춘다.
- `둘 다 아닌 것 같아요`는 E로, `사진 다시 보기`는 입력 V로 이동한다. E는 `후보 다시 보기` / `사진 다시 보기` / `다른 대상 알아보기`를 제공한다.
- 후보 선택 후 A에는 선택한 건물 이름과 그 건물의 검수된 참고 사진·설명을 보여준다. 원래 입력 사진을 선택한 후보의 확정 사진처럼 다시 이름 붙이지 않는다. `후보 다시 비교하기`로 C에 돌아갈 수 있다.
- 실제 정답 판정은 진행자의 관찰지에서 한다. 참여자에게 정답 표시를 하거나, 오답 선택을 자동 교정하지 않는다. 선택 이유와 실제 정답을 별도로 기록한다.

```text
←                  홈
어느 건물과 닮았나요?
[알아보는 사진 · 확대]
[후보 A 참고 사진]
이름 / 보이는 특징 1~2개
[이 건물이에요]
[후보 B 참고 사진]
이름 / 보이는 특징 1~2개
[이 건물이에요]
둘 다 아닌 것 같아요 / 사진 다시 보기
```

### 3.2 A/N — 설명 이후 탐색

A의 정보 순서는 선택 대상·사진 → 짧은 설명 → 더 읽기·출처 → 관련 질문 → 다음 행동 → 선택적 다음 관람 제안이다. 완료 팝업이나 강제 추천을 띄우지 않는다.

| 요소 | 문구·행동 | 표시 조건 |
| --- | --- | --- |
| 같은 대상의 추가 설명 | `관련 질문 더 보기` → Q | 검수된 관련 질문이 1개 이상 |
| 같은 사진 재선택 | `같은 사진에서 다른 부분 보기` → V | 현재 설명 장면에 지원 부분이 있을 때 |
| 후보 선택 수정 | `후보 다시 비교하기` → C | 후보 비교에서 이어진 설명·질문 답변일 때 |
| 새 탐색 주 행동 | `다른 대상 알아보기` → N | A 및 필요한 복구 화면 |
| 다음 관람 제안 | 큰 사진 → 이름 → 자연스러운 소개 1문장 → `살펴보기` | 검수된 연결이 있을 때 최대 1개 |
| 홈 | 상단 `홈으로` → 현재 장면 H | 실행 초기화와 구분 |

후보 비교로 들어온 A의 ‘같은 사진’은 **현재 표시 중인 후보 참고 사진**이다. 지원 부분이 없으면 이 버튼은 숨긴다. 원래 입력 사진으로 돌아가는 경로는 `후보 다시 비교하기` 안에 둔다.

N은 검색 엔진이나 갤러리 제품 기능을 구현한 화면이 아니다. 제목 `다른 대상 알아보기`, 안내 `촬영 대신 준비된 사진으로 체험해요.` 아래 현재 장면을 제외한 검수된 예시 사진 최대 3개를 제공한다. 중립적인 장면 이름을 쓰고 정답 건물 이름을 미리 요구하지 않는다. 사진을 고르면 그 장면 V로 이동한다. 장면이 없으면 `이번 체험에서 준비된 다른 사진이 없어요`와 뒤로·홈을 제공한다. 작동하지 않는 촬영/업로드/검색 버튼은 넣지 않는다.

N에는 ‘새로운 촬영 입력을 정적 예시로 대체했다’는 한계가 있다. N의 사진 고르기를 실제 검색·촬영의 사용성 결과로 평가하지 않는다.

다음 관람 제안은 별도 정적 연결이다. 실제 주변 관계를 검수한 경우에만 제목을 `이 근처에서 이어서 볼까요?`로 쓴다. 관계를 확인하지 못한 경우 `이런 곳도 살펴보세요`라는 관련 대상 제안으로 낮추고, 주변/최단 경로/몇 분/몇 m라고 쓰지 않는다. 둘은 관찰 결과에서도 구별한다. 같은 대상 재추천은 금지한다. 안내에 `테스트에서 정한 구역의 예시입니다`를 표시하고 실제 위치 추정처럼 표현하지 않는다.

```text
[선택 대상 사진·이름]
짧은 설명 / 더 읽기 / 출처
관련 질문 더 보기 →
같은 사진에서 다른 부분 보기
[다른 대상 알아보기]
이 근처에서 이어서 볼까요?  (검수된 경우만)
[큰 사진]
대상 이름 · 소개 한 문장
살펴보기 →
```

모든 행동을 큰 주 버튼으로 만들지 않는다. 새 탐색을 주 행동으로, 같은 사진·후보 수정은 텍스트 행동으로 구분한다. 다음 관람 제안은 본문을 읽은 뒤 보이는 위치에 둔다. 선택하지 않고 관람을 계속하는 것도 정상 종료다.

### 3.3 Q/E — 준비된 질문과 지원 한계

- 기본 설명을 먼저 제공한다. Q를 필수 단계로 만들지 않는다.
- 질문은 테스트 대상별로 실제 자료에 답이 있는 1~2개를 준비한다. 개수를 채우기 위한 사실·질문 생성은 하지 않는다. Q에는 질문 문장 자체가 선택 항목이다.
- Q에서 선택한 답은 동일 대상의 A로 연결한다. 질문 제목, 답변, 출처와 `기본 설명으로`를 제공한다.
- 질문 0개 대상: A에서 `아직 준비된 추가 질문이 없어요`를 표시하고 Q 진입을 숨긴다. Q에 직접 복원된 경우도 빈 상태와 기본 설명 복귀를 제공한다.
- 질문이 있는 Q에는 `찾는 질문이 없어요`를 제공한다. E 문구: `이 질문에 대한 설명은 아직 준비되지 않았어요.` 기본 설명·다른 부분·다른 대상 경로를 대상 상태에 맞게 표시한다.
- 질문 0개 안내에서도 `궁금한 내용이 없어요`를 통해 같은 미지원 상태로 갈 수 있다. 빈 콘텐츠와 사용자가 충분히 이해한 상태를 동일하게 집계하지 않는다.
- 참여자는 자유 질문을 앱에 입력하지 않는다. 진행자는 설명 전 궁금한 내용, 설명 후 남은 내용을 관찰지에 기록한다. 즉석 검색·답변으로 과업 성공을 만들지 않는다.

## 4. 콘텐츠 계약의 변경안

P02에서 `schemaVersion: 2`로 변경하고 P01 자료를 기존 콘텐츠와 함께 이관했다. v2만 명시적으로 읽으며 v1은 거부한다. 기존 S1~S3 ID·사진·기본 설명을 보존했다. 기존 Source/Asset/Target/Question/Answer 계약을 재사용하며 SQL·DB·API를 추가하지 않는다.

| 추가/확장 자료 | 필드 | 규칙 |
| --- | --- | --- |
| Dataset | `comparisonCases`, `continuations` | v2의 배열. 사용하지 않으면 빈 배열 |
| ComparisonCase | `id`, `inputSceneId`, `options`, `reviewStatus`, `checkedAt` | 입력 장면 1개, 옵션 정확히 2개, 별도 S4에서 사용 |
| ComparisonOption | `id`, `targetId`, `referenceSceneId`, `clues` | 두 옵션의 대상은 서로 다르고 building. 참고 장면에 해당 대상이 있어야 함 |
| Clue | `text`, `sourceIds` | 1~2개. 원문 근거와 입력/참고 사진의 가시성을 함께 검수 |
| Continuation | `id`, `fromTargetId`, `toSceneId`, `toTargetId`, `intro`, `relation`, `sourceIds`, `reviewStatus`, `checkedAt` | 출발 대상당 최대 1개. relation은 nearby/related. 목적지의 검수된 기본 설명으로 연결 |
| TestPreset 확장 | `navigationScenes`, `comparisonCaseId` | 기존 필드 유지. 비교 없으면 null. 허용 이동 목록에 시작 장면 포함 |
| NavigationScene | `sceneId`, `contextKey`, `cardVisible`, `selectableInNewExplore` | preset 안에서 sceneId 유일. 새 탐색 목록과 허용 이력 범위를 구분 |

옵션 사진은 `referenceSceneId → assetId`, 이름·설명은 `targetId`에서 읽는다. 중복 복사 필드를 만들지 않는다. 입력 장면에 틀린 후보를 실제 대상으로 넣어서 기존 검사를 우회하지 않는다. 입력 사진의 실제 대상 연결은 유지하되 S4의 V/C에는 정답 라벨을 노출하지 않는다. alt는 대상 외형을 중립적으로 설명하고 관찰 정답표는 앱 bundle 밖의 진행자 기록에 둔다. 정답 은닉은 보안 기능이 아니며 개발자 도구로 정답을 찾는 테스트도 아니다.

NavigationScene에는 비교 후보의 참고 장면도 포함할 수 있지만 `selectableInNewExplore=false`로 두어 새 탐색 목록을 불필요하게 늘리지 않는다. Continuation 목적지는 실행 preset의 허용 목록에 있을 때만 표시한다. N에서는 같은 sceneId를 제외한다. 후보 비교는 `preset.comparisonCaseId`가 가리키는 입력 장면의 명시적 행동에서만 시작한다.

필수 검사:

1. ID·참조·기존 답변/출처·사진 조건을 유지하고 새 배열을 `indexContent`에 포함한다.
2. 후보 target/referenceScene, 기본 설명, 사진 이용 조건이 일치한다. clue는 출처가 있고 reviewed case만 관찰에 사용한다.
3. 두 후보가 같은 대상이거나 입력 장면이 없거나 옵션이 1/3개인 자료는 실패시킨다. 현재의 부분 영역 중첩 거부 규칙은 유지한다.
4. `navigationScenes`의 시작 항목은 preset의 scene/context/card와 일치한다. URL/테스트 설정으로 시작 맥락을 바꾸면 그 항목도 함께 검증·정규화한다. 나머지 목적지는 해당 preset에 지정한 맥락만 사용한다.
5. Continuation은 출발≠도착 대상, 목적지 장면·대상·기본 설명이 일치해야 한다. nearby는 실제 위치 관계의 근거를 추가 검수한다. reviewed만 화면에 표시한다.
6. 검수 전 자료는 개발 fixture로만 사용한다. 모든 후보/질문/다음 관람 연결의 사람 관찰 가능 여부는 각 자료의 검수 상태로 판정한다.

## 5. 상태 전환·뒤로 가기 계약

기존 상태 필드는 유지하고 `comparisonCaseId: null|string`, `comparisonOptionId: null|string`을 추가한다. `sceneId`는 현재 표시할 장면이다. 원래 비교 입력 장면은 case의 `inputSceneId`에서 얻는다. target/question/answer를 각 화면이 따로 저장하지 않는다. `entryOrigin`에는 기존 값 외에 candidate/continuation을 추가한다. N은 현재 장면을 유지한 채 선택을 기다리는 화면이다.

| 행동 | 다음 상태 | 초기화·검증 |
| --- | --- | --- |
| `compare` | C, scene=inputSceneId, case 설정 | 해당 preset과 입력 장면 확인. target/question/answer/point/option 초기화 |
| `choose-candidate(optionId)` | A, scene=referenceSceneId, target=옵션 대상 | 허용 옵션·장면·답변 검증 후 원자적으로 scene/context/card/target/answer 변경. case/option 유지 |
| `compare-again` | C, scene=case.inputSceneId | 설명·질문·point 초기화. 기존 option은 중립적인 ‘이전에 고른 후보’ 표시로만 유지 |
| `no-candidate` | E, error=no-candidate, 입력 장면 | target/question/answer/option 비움, case 유지 |
| `retry-comparison-photo` | 입력 V | case는 유지, option/선택/답변 비움. 다시 compare 가능 |
| `new-explore` | N | 출발 scene과 상태 유지. 뒤로 가면 원래 설명으로 복귀 |
| `choose-scene(sceneId)` | 목적지 V | 허용·selectable 장면 확인. scene/context/card를 함께 변경, target/question/answer/point/case/option 초기화 |
| `open-continuation(id)` | 목적지 A | 현재 target의 연결인지 확인. 목적지 맥락·검수된 기본 설명을 함께 설정, 이전 질문/point/case/option 비움 |
| `view` (다른 부분) | 현재 장면 V | 선택·답변·비교 상태 비움. 후보 입력 재검토는 별도 행동 사용 |
| `question` / `overview` | 같은 대상 A | 질문↔답변 일치 검증. 비교에서 이어진 경우 case/option 유지 |
| `home` | 현재 장면 H | target/question/answer/point/case/option 초기화. runId 유지 |
| 진행자 실행 초기화·새로고침 | 시작 preset H | 새 runId. 이전 실행 이력 무효화 |

모든 새 scene 설정은 NavigationScene에서 맥락을 함께 가져온다. 이전 구역 배지·홈 카드·선택 테두리를 남기지 않는다. 불법 ID 행동은 기존 상태를 유지하고 개발 검사에서 확인한다. 유효한 참조의 설명/출처가 실행 중 누락되면 기존 E 복구를 사용한다.

현재 `openAnswer`가 먼저 읽은 scene을 캡처하므로, 다른 장면에 답을 열 때 그 클로저를 그대로 사용하면 안 된다. 검증한 목적지 상태를 만든 후 그 목적지 scene으로 답변 연결을 검사한다. ‘모든 target을 모든 scene에서 허용’하는 방식으로 수정하지 않는다.

### 이력·URL·복원

- 사용자 장면 이동, 후보 선택, N, 홈 이동은 같은 run 안에서 history에 추가한다. 부분 위치의 연속 선택은 기존처럼 replace한다.
- `startRun`은 진행자 reset/preset 변경/초기 로드에 한정한다. 기존 `home → startRun` 분기를 제거하는 것이 구현 변경점이다. 홈에서 브라우저 뒤로는 직전 설명으로 돌아간다.
- URL은 실행 preset과 시작 설정을 유지한다. 새로고침하면 그 실행의 시작 H로 돌아간다는 것을 테스트 안내에 명시한다. 장면별 깊은 링크·영구 복원은 추가하지 않는다.
- `canRestore`는 runId 확인에 더해 현재 preset의 navigationScenes에 scene이 있는지, scene에 맞는 context/card인지 검사한다. `scene === preset.scene` 조건만 제거하고 모든 장면을 허용해서는 안 된다.
- A/Q는 현재 scene-target-question-answer 관계를 검사한다. C와 no-candidate E는 case/preset/inputScene 관계를 검사한다. 후보 A/Q/E는 option-target-referenceScene 관계도 검사한다. N은 출발 상태의 참조를 검사한다.
- 다른 실행·삭제된 자료·잘못된 snapshot은 시작 H로 교체한다. 테스트 설정 화면을 일반 뒤로 경로에 섞지 않는다.
- 정상 복원 시 해당 history 항목의 화면 스크롤과 사진 확대/내부 스크롤을 복구한다. viewport가 바뀌면 유효 범위로 제한한다. 전진 이동은 제목으로 포커스, 뒤로는 가능한 원래 조작부로 복귀하고 없으면 제목으로 이동한다. 초기 렌더의 `scrollTo(0,0)`가 복원값을 덮지 않게 한다.

## 6. 표현·접근성

[DESIGN](../DESIGN.md)의 흰 바탕·기와 먹청색·작은 주홍 포인트를 유지한다. 연한 초록·누런 배경을 새 상태 색으로 사용하지 않는다. 기존 CSS+SVG 유리는 버튼 등 조작층에만 재사용하고 사진·설명 전체를 필터로 감싸지 않는다. 유리용 Canvas·새 모션 라이브러리는 추가하지 않는다.

후보는 320px에서도 세로로 읽고 고를 수 있어야 한다. 사진 잘림으로 구별 단서가 사라지지 않도록 contain 또는 검수된 구도를 사용한다. 관련 질문/새 탐색/추천 카드는 중첩 버튼 없이 한 행동 단위를 유지한다. 선택을 색만으로 표시하지 않고 텍스트·테두리를 함께 쓴다. 44px 이상 터치 영역, 키보드 조작, 200% 글자 확대와 reduced-motion을 확인한다.

사진 이동 효과는 같은 asset인 경우에만 기존 전환을 재사용한다. 입력 사진이 다른 후보 참고 사진으로 변신하거나 다른 건물 사진끼리 이어지는 모션은 사용하지 않는다. 변형 효과가 끝나야 행동을 할 수 있는 대기 상태를 만들지 않는다.

## 7. 구현 작업 분할

구현할 때 실행할 기존 명령: `prototype/`에서 `npm.cmd test`, `npm.cmd run build`(콘텐츠 검사 포함). 통합 브라우저 확인은 아래 대표 경로를 한 번씩 검사하고, 새 실패가 있을 때 관련 범위만 반복한다. 명령 성공만으로 실기기·사람 관찰을 완료하지 않는다.

| G03 | S4→해당 없음→사진 다시 보기→후보 | 입력 사진 유지, 잘못된 설명 강제 없음, 재시도 가능 |
| G04 | 설명 A→N→장면 B→설명 B→뒤로 | B 선택 상태, N, A가 시간순 복원. 맥락·사진·답변이 섞이지 않음 |
| G05 | 설명→다음 관람 제안→질문→뒤로 | 목적지의 대상·질문 일치, 원래 설명까지 복귀 가능 |
| G06 | Q에 질문 0/1/2개, 미지원 질문 | 빈 버튼 목록 없음, 기본 설명/새 탐색으로 복귀. 없는 답을 비슷한 답으로 대체하지 않음 |
| G07 | 후보/장면 변경 후 질문, 악성·오류 ID | 허용하지 않은 참조 거부, 다른 대상 답변 노출 없음 |
| G08 | 홈→뒤로 / reset→이전 history / 새로고침 | 홈은 직전 화면 복귀 가능. reset/새로고침은 이전 run 복구 거부 |
| G09 | 추천 없음·허용 목적지 없음·이미지 실패 | 빈 대형 영역·죽은 버튼 없이 안내와 복구. 미검수 nearby 없음 |

## 9. 사람 관찰 준비와 백로그 연결

기존 [TESTING](TESTING.md)의 중립적 진행·개입 수준·기록 양식을 유지한다. 다음은 보완 후 적용할 관찰안이며 현재 테스트를 수행했다는 기록이 아니다.

| 상황 | 진행문·방법 | 기록할 것 |
| --- | --- | --- |
| 기존 전체/부분 탐색 | 기존 S1/S2, 먼저 원하는 대상·궁금증 확인 | 대상 지정, 설명 이해, 준비된 질문의 적합성, 미지원 |
| 설명 이후 자유 행동 | 설명을 읽은 뒤 우선 행동을 기다림. 필요할 때 `이제 무엇을 하려고 하나요?` | 관람 종료/같은 부분/다른 대상/다음 관람 의도와 실제 경로 |
| 새 탐색 보조 과업 | 자발적 관찰 뒤에만 `다른 대상이 궁금해졌다고 생각하고 이어서 알아봐 주세요.` | N 진입·새 장면·되돌아감. 자발적 선택과 분리 |
| 기존 홈 호기심 카드 | S3 유지. 다음 관람 연결과 다른 상황으로 기록 | 발견/무시/설명 뒤 재관찰. 클릭을 관심 증가로 단정하지 않음 |
| 후보 비교 S4 | `이 사진의 건물이 무엇인지 화면의 자료로 확인해 주세요.` | 정답 여부, 선택 근거, 확신 이유, 망설임·해당 없음 |
| 보조 복구 | 자연스러운 오류가 없었을 때만 별도 확인 | 후보 수정·질문 없음·다른 대상 이동의 복구 가능성 |

S4는 정해진 과업 뒤에 두고 앞서 정답을 학습한 사진을 피한다. 불가피하게 재사용하면 학습 영향을 기록한다. 후보 표시 순서는 실행 전에 고정해 기록한다. 한 사람에게 반복한 전후 비교를 A/B 효과로 주장하지 않는다.

다음 관람 연결의 대상이 S3 굴뚝이면 S3를 먼저 수행하거나 다른 연결을 선정해 첫 발견 관찰이 오염되지 않게 한다. 테스트 중 참여자의 선택에 맞춰 정답·카드·자료를 몰래 교체하지 않는다.

관찰지에는 기존 항목 외에 `시작 scene`, `진입 경로`, `다음 행동 의도`, `후보 선택/실제 정답/선택 이유`, `자발적·보조 과업`, `준비된 결과의 한계`를 추가한다. 답변을 봤다는 것과 궁금증 해소를 구분한다. 원본 발화나 개인 식별정보를 공개 문서에 넣지 않는다.

백로그로 옮길 때는 관찰 사실 → 해석 → 요구사항 변경/유지 → User Story·AC → 미검증 사항을 연결한다. 예: ‘설명 뒤 새 탐색을 찾느라 홈을 여러 번 오감’은 직접 진입 요구의 근거가 될 수 있지만 추천 알고리즘 필요성의 증거는 아니다. 관찰하지 않은 기존 핵심 요구사항도 백로그에 남기고 미검증으로 표시한다.

## 10. 설계 인계와 종료 범위

읽는 순서: 이 문서 → SCREENS/DATA의 기존 계약 → 현재 코드 → R 작업의 자료·인수 조건. 이 문서의 추가 계약은 보완 구현 시 적용하며, 실제 구현 뒤 기존 원본 문서의 해당 절과 상태 표시를 함께 갱신한다. 중복된 두 계약을 계속 유지하지 않는다.

설계 뒤 기존 P 이슈로 통합했고 P01 자료 준비와 P02 v2·N·이력을 진행했다. P03~P07의 후속 보완·통합·기기 확인, P08 사람 관찰과 Product Backlog 반영은 별도다. 새로운 채팅으로 전달하거나 작업자를 자동 실행하지 않는다. 커밋·푸시·Wiki 게시는 실제 수행한 결과만 보고한다.

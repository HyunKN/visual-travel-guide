# Sol 구현 인계와 AI Workflow 기록

**현재 요청은 P02 구현이다.** P01 자료를 v2 `2026-10-16-scenes.2`로 병합하고 N 새 탐색·허용 장면 이동·홈/뒤로 이력·스크롤/확대/포커스 복원을 연결했다. 현재 변경·검사는 [P02](https://github.com/HyunKN/visual-travel-guide/issues/7)와 [검증 기록](../../prototype/VERIFICATION.md)을 확인한다. P03 후보 UI, P04 지원 한계 보완, P05 다음 관람 카드는 후속이다. 기존 P 이슈를 사용하고 R 단계를 별도 이슈로 늘리지 않는다. 다음 요청 시 실제 미커밋 diff부터 확인하며 아래 최초 프롬프트로 추가 구현 권한을 확대하지 않는다.

현재 구현 인계: 이 채팅에서 모바일 웹과 세 장면 자료를 구현했다. 계속 작업할 때는 [실행 안내](../../prototype/README.md)와 [검증 범위·남은 항목](../../prototype/VERIFICATION.md)을 먼저 읽고 실제 미커밋 파일을 확인한다. 아래 시작 요청은 최초 설계 인계문이며 새 앱을 중복 생성하라는 지시가 아니다. 다른 채팅에 메시지를 보내거나 Sol을 별도로 실행하지 않았다.

유리 재질의 최신 계약은 [재질 문서 11절](../design/INTERACTION_MATERIALS.md#11-css--svg-볼록-컨테이너-적용-2026-10-16)을 따른다. 외곽 14px의 볼록 SVG 굴절을 적용하며 유리용 Canvas는 사용하지 않는다. P07의 실기기 확인과 P08의 사람 관찰은 코드·데스크톱 검사와 분리한다.

현재 인계 연결: [설계 PR](https://github.com/HyunKN/visual-travel-guide/pull/5) · [상위 Issue](https://github.com/HyunKN/visual-travel-guide/issues/4) · 첫 작업 [P01 콘텐츠](https://github.com/HyunKN/visual-travel-guide/issues/6) / [P02 첫 흐름](https://github.com/HyunKN/visual-travel-guide/issues/7). 설계 브랜치는 `codex/prototype-scenario-design`, 본문 설계 기준 커밋은 `03b4c2b176664f74c136e3a5d43bc4294d96eb85`다. URL 연결은 그 뒤 커밋에서 보완되므로 시작 때 PR 최신 head와 실제 로컬 상태를 확인한다.

## 1. 이 인계에서 고정할 것

- 목표: 준비된 경복궁 장면에서 **건물 전체와 문양·구조물 탐색 → 이름·짧은 설명 → 관련 질문**, 그리고 선택적인 홈 카드 경로를 관찰할 수 있게 만든다.
- 범위: [설계 시작점](README.md), 작업별 [P01~P08](TASKS.md). Sol의 코드 작업은 P01~P07이며 P08은 사람과 수행한다.
- 질문 방식: 기본 설명 먼저, 원하면 준비된 관련 질문 선택. 자유 텍스트 입력·LLM·진행자 응답 큐는 포함하지 않는다.
- 자료 출처: [콘텐츠 원본](content/README.md)의 궁능유적본부 사진 2개와 **사용자가 고른 한국민족문화대백과사전 미디어 `7b8dca9e`**를 사용한다. 세 사진의 개별 공공누리 제1유형 표시·실제 픽셀·해시를 확인했다. 촬영일은 모두 미상이며 사용자 최종 확인과 실기기 판독성은 별도다.
- 시각 방향: [DESIGN](../DESIGN.md)의 흰 바탕·둥근 UI·기와 먹청색 중심·작은 주홍 포인트. [실제 참고](VISUAL_REFERENCES.md)와 [제외 시안·방지 기준](ANTI_SLOP.md)을 함께 읽는다. 토큰은 실제 CSS에 정의했다. 이전 미색 생성 시안은 구현 기준이 아니다.
- 상태: 로컬 앱·콘텐츠 구현과 자동/브라우저 검사를 진행했다. 실기기·사용자 콘텐츠 확인·사람 관찰은 별도다. 실제 범위와 명령은 위 실행 안내를 우선한다.
- 설계 조사 기준 커밋: `2c350649260a480864b754178ac0976356c961aa`. 이 커밋만 checkout하면 새 설계가 없다. 아래 시작 정보에는 **설계가 실제 포함된 버전**을 적는다.

## 2. 전달 전에 채울 정보

| 항목 | 확인 방법 |
| --- | --- |
| 상위 Issue 및 시작할 하위 Issue URL | 발행한 실제 URL을 사용. 없으면 사용자 승인 작업 요청과 로컬 설계 경로를 사용 |
| 설계 PR/커밋 | `git log`와 PR의 파일 목록으로 설계 포함 여부 확인 |
| 구현 기준 브랜치·커밋 | 설계 병합 이후 커밋 또는 설계 브랜치를 명시 |
| 미커밋 설계로 인계하는 경우 | 같은 checkout과 변경 파일 목록을 전달. 새 worktree로 자동 복사되지 않음 |
| 기존 앱·사용자 변경 | 실제 status와 구현 문서 확인. 다른 작업자의 변경 보존 |
| 콘텐츠 상태 | reviewed 자료의 유무, P01/P06 남은 조건 |
| 검사 도구와 기기 | 실제 설치 환경·사용 가능한 브라우저, 실기기는 별도 확인 |

미확정 URL을 가짜 Issue 번호로 채우지 않는다. 설계가 공유되지 않은 상태에서 오래된 main 문서만 보고 구현하게 하지 않는다.

## 3. Sol에게 전달할 시작 요청

아래 요청에는 현재의 Issue와 설계 PR을 넣었다. 전달 직전에 최신 head·실제 checkout을 확인한다. 작업 요청의 제품 조건은 이 문서 작성에 대한 사용자 요청과 이후 승인된 범위를 따른다.

```text
작업 종류: 시나리오 기반 프로토타입 구현
목적: 경복궁의 건물 전체와 문양·구조물을 탐색해 이름·짧은 설명·출처를
확인하고, 원하면 관련 질문이나 홈의 호기심 카드로 이어지는 흐름을 만든다.

작업 Issue URL: https://github.com/HyunKN/visual-travel-guide/issues/4
첫 작업: P01 https://github.com/HyunKN/visual-travel-guide/issues/6
자료 확보가 지연되면 P02 https://github.com/HyunKN/visual-travel-guide/issues/7
기준 PR: https://github.com/HyunKN/visual-travel-guide/pull/5
기준 브랜치: codex/prototype-scenario-design
설계 본문 기준 커밋: 03b4c2b176664f74c136e3a5d43bc4294d96eb85
이후 링크 보완 커밋을 포함한 PR 최신 head를 확인한 뒤 시작해라.

먼저 AGENTS.md와 docs/DEVELOPMENT.md, docs/QUALITY.md,
docs/prototype/README.md, docs/prototype/TASKS.md를 읽어라.
UI 작업은 docs/DESIGN.md, docs/prototype/VISUAL_REFERENCES.md,
docs/prototype/ANTI_SLOP.md도 읽어라. 흰 바탕·둥근 UI·기와 먹청색
중심·작은 주홍 포인트를 지키고 누런 배경과 이전 미색 생성 시안은 사용하지 마라.
아직 최종 시안은 미정이므로 합의된 방향을 바탕으로 시안을 선택한 뒤 구현한다.
전통 문양을 직접 표현하는 것은 가능하다. 굿즈의 색 조합·표현 방식은 참고하되,
해당 업체의 상품 사진·상세 이미지·상품 일러스트를 앱 자산으로 가져오지 마라.
상품 사진에서 문양을 잘라 쓰는 것도 피하고, 참고는 원본 링크로 유지해라.
실제 외부 이미지를 채택할 때는 DATA의 Asset 계약에 따라 이용 조건을 확인해라.
선택한 작업에 연결된 SCREENS/DATA/TESTING만 추가로 읽고
현재 Git 상태와 Issue를 확인한 뒤 작은 실행 계획을 알려줘.

구현 범위는 P01~P07이다. 준비된 사진·영역·검수된 설명을 사용한다.
사용자가 부분을 직접 고르고 수정하는 동작을 구현하고,
대상·질문·답변·출처가 일관되게 연결되도록 검증해라.
기본 설명을 먼저 보여주고 추가 질문은 준비된 질문 선택으로 처리한다.
홈 주요 행동 하나와 카드 최대 하나를 유지해라.

자동 인식, LLM, 실제 GPS, 자유 사진 업로드, 서버/DB,
자유 질문 입력, 원격 진행자 큐, 계정·설치 유도·지도는 범위 밖이다.
콘텐츠를 확보하지 못했으면 개발용 예시임을 명시하고,
그 상태로 사람 관찰 준비가 완료됐다고 보고하지 마라.

작업별로 인수 조건·관련 실패 경로를 확인하고 Issue/PR에 증거를 남겨라.
기술 선택은 가장 작은 구성을 우선하되 실제 설치 버전·명령을 검증해라.
다른 작업자의 변경을 보존하고 관련 문서를 함께 갱신해라.
요청 범위에 없는 다른 채팅 생성·메시지·배포·병합은 자동으로 수행하지 마라.

검증 구분:
- AI: 자료·상태·브라우저·접근성 범위의 실제 수행 검사.
- 사람: 실기기와 S1~S3 관찰. 수행 전에는 미실행으로 기록.

완료 보고: 실제 변경, 실행 방법, 검증 환경·기대/실제 결과,
미확인 항목, 문서 영향, 다음 작업 Issue와 기준 커밋.
P08 사람 관찰을 AI가 대신 실행한 것처럼 완료하지 마라.
```

사용자가 첫 작업 하나만 맡기면 해당 P 작업 종료 시 인계한다. P01~P07 묶음을 명시적으로 맡겼다면 앞선 검증이 끝난 뒤 선행 조건이 충족된 다음 작업으로 진행한다. 새로운 제품 범위가 필요한 문제만 사용자에게 확인한다.

## 4. 작업 완료 보고 양식

```text
작업 / 상위·하위 Issue 전체 URL:
기준 버전 / 결과 커밋·PR 또는 미커밋 파일:
사용자가 새로 할 수 있는 행동:
실제 변경 파일과 읽는 순서:
입력 → 처리 → 저장(없으면 없음) → 화면 결과:
실행·검사 명령 / 기기·환경:
인수 조건별 기대 / 실제 결과 / 통과·실패·미실행:
문서 영향과 갱신:
남은 미정 사항·위험·실기기/관찰 제한:
다음 작업과 선행 조건:
```

완료 상태의 원본은 Issue, 코드·검사 증거는 PR이다. 공통 문서에는 반복 사용하는 규칙과 실제 구조·명령만 반영한다.

## 5. AI Workflow 채팅에 전달할 요약

전달할 때 문서·Issue·PR의 실제 링크와 검증 결과를 채운다. 사적인 대화나 원본 자료 대신 아래 작업 정보만 전달한다.

```text
프로토타입 작업의 상세 설계를 docs/prototype/에 정리했다.
범위는 건물 전체/문양·구조물 탐색 → 기본 설명 → 준비된 관련 질문과
선택적인 호기심 카드다. 자동 인식·LLM·실제 위치는 모사 범위 밖이다.

작업은 P01~P08로 나누고 P01~P07의 구현·준비와 P08 사람 관찰을 구분했다.
기존 Issue·PR·Wiki 운영을 사용하며 별도의 진행 TODO를 만들지 않는다.

설계 문서/버전: [실제 링크]
상위/하위 Issue: [실제 링크 또는 미발행]
설계 PR: [실제 링크 또는 미생성]
확인한 문서 검사: [실제 결과]
Sol 인계문: docs/prototype/HANDOFF.md

이 메시지는 작업 기록·컨텍스트 연결을 위한 것이다.
추가 제품 구현, 다른 채팅 전달, 병합·배포를 지시하는 것은 아니다.
공통 Workflow 규칙과 충돌이 있다면 해당 근거와 수정 제안을 이 채팅에 남겨줘.
```

## 6. 게시·기록 순서

1. 상세 설계와 영향받은 공통 문서를 같은 변경으로 준비한다.
2. 문서 링크/기존 Wiki 변환 검사/변경 범위를 확인한다.
3. 사용자가 승인한 게시 범위에서 설계 PR과 작업 Issue를 연결한다. PR 생성 시 현재 Codex 작업에 PR을 첨부한다.
4. 설계 PR이 아직 병합되지 않았다면 Sol은 그 브랜치의 설계를 읽는다. Wiki를 최신 작업 브랜치로 간주하지 않는다.
5. main 병합이 수행되면 기존 Docs and Wiki 자동화 결과와 게시 기준 커밋을 확인한다. PR 생성만으로 Wiki 게시 완료라고 보고하지 않는다.
6. 실제 링크와 검증 결과로 이 채팅·AI Workflow 채팅·Sol 시작 요청이 같은 버전을 가리키게 한다.

← 테스트 안내와 기록지 열기

프로토타입 테스트를 진행하는 방법

2026-10-17 조사·작성 · 실제 참여자 관찰은 이 문서 작성과 별도입니다.

먼저 제작자가 앱의 동작을 확인하고, 참여자와는 목적을 달성하는 과정을 관찰합니다. 그 결과로 기능과 안내를 고칩니다. 다음 버전에서도 같은 방법을 반복할 수 있도록 정리한 안내입니다.

현재 테스트지는 시작 화면·해볼 일·메모 중심의 간단한 양식입니다. 아래 방법은 진행자 참고용이며 모든 분류를 현장에서 채울 필요는 없습니다. 문제 분류와 백로그 판단은 테스트 후 정리합니다.

이번에는 앱 안에 준비된 사진만 사용합니다. 외부 화면이나 인쇄 사진을 따로 준비할 필요가 없습니다. AI 인식·GPS·실제 현장 관람 효과는 이번 결과로 평가하지 않습니다.

1. 언제 조작 순서를 보여주나요?

제작자 기능 확인 — 순서를 보고 확인

약속한 화면과 내용이 나오는지 봅니다. 시작 화면 → 누를 것 → 다음 화면 → 끝 화면을 따라가며 기대와 실제를 비교합니다.

첫 사용 관찰 — 시작 화면과 목표를 먼저 전달

참여자가 어디서 시작해서 무엇을 이루면 되는지 명확하게 말합니다. 누를 버튼과 순서는 미리 알려주지 않고 실제로 어떤 길을 찾는지 봅니다.

보조 과업 — 첫 시도가 끝난 뒤 순서를 함께 확인

처음에 못 본 출처·관련 질문·뒤로가기 등을 함께 확인합니다. 안내 후 따라 한 결과는 처음부터 스스로 찾은 결과와 따로 기록합니다.

ISTQB는 QA를 절차 개선, testing을 제품 평가로 구별합니다. 이 안내는 두 활동을 연결하되 기능 동작과 첫 사용 이해의 결과를 섞지 않는 운영안입니다. 정의 근거

2. 한 번의 테스트는 이렇게 진행해요

  1. 제작자 먼저: 접속과 S1~S5의 참고 순서를 확인합니다. 앱이 안 열리면 시작을 미루고 환경 문제로 적습니다.
  2. 설명: “앱이 이해하기 쉬운지 보는 자리이고 정답 시험은 아닙니다. 편하면 생각을 말해주세요.”라고 안내합니다.
  3. 목표 전달: 진행자가 테스트지의 시작 화면까지 준비하고 ‘해볼 일’을 읽어줍니다. 목표 수행에 필요한 버튼 순서는 먼저 알려주지 않습니다.
  4. 관찰: 실제로 누른 것, 망설인 곳, 발언을 기록합니다. 계속 말하도록 강요하지 않습니다.
  5. 첫 시도 마무리: 완료하거나 그만하려 하면 결과와 받은 도움을 먼저 기록합니다.
  6. 함께 확인: 필요할 때만 못 본 동작을 첫 시도 뒤 함께 확인합니다. 준 도움은 메모에 남깁니다.
  7. 정리·수정: 사실과 해석을 나누고 기존 백로그 후보에 연결합니다. 수정 후 같은 경로와 관련 이동을 다시 확인합니다.

한 명의 진행자와 한 명의 참여자로, 20~30분 정도부터 시작하는 것을 제안합니다. 시간·도움 분류·영향 분류는 우리 프로젝트의 운영 선택입니다. 혼자 하면 첫 사용 관찰 대신 제작자 리허설로 기록합니다.

제작자 자유 탐색은 목표 메모(test charter)를 두고 진행할 수 있습니다. 예: “5분 동안 설명→다른 사진→뒤로가기를 살피며 대상·설명이 섞이는지 확인한다.” 시간·범위·목표와 실제 경로·발견을 남깁니다. 경험 기반 기법인 탐색적 테스트를 적용한 것이며, 5분은 우리 제안입니다.

3. 과업을 만들 때 적을 것

시작 화면
“홈 화면”, “경회루 설명 화면”처럼 실제 화면 이름을 적습니다.
상황과 목표
왜 이 행동을 하며 무엇을 알아보면 되는지 말합니다. 예: “연못 앞 건물이 어떤 곳인지 알아보세요.”
끝낼 기준
설명을 확인했거나, 더 진행하기 어렵다고 하면 첫 시도를 끝냅니다.
진행자 참고 순서
시작 화면 → 행동 → 다음 화면 → 끝 화면을 적고 첫 시도 동안 접어둡니다.
추가 점검
출처·관련 질문·되돌아오기처럼 첫 시도 뒤 함께 확인할 내용을 적습니다.

목표를 흐릿하게 만들 필요는 없습니다. 다만 “이 버튼을 누르세요”라고 먼저 말하면 그 버튼을 스스로 찾을 수 있는지는 관찰하기 어렵습니다. 과업 작성 근거

S1~S5는 기존 ID를 유지합니다. 제작자는 홈에서 사진을 열어 연습합니다. 함께하는 S1/S2/S4는 진행자가 사진 화면까지 준비한 뒤 시작합니다. 사진 준비 도움과 이후 조작 도움을 따로 적고, 미리 준비한 홈→사진 경로를 참여자가 스스로 발견했다고 해석하지 않습니다. 홈 경로는 맨 처음 자유 탐색에서 봅니다. 이름 검색은 선택적 추가 점검입니다.

4. 어떤 도움을 줬는지 적어요

  • 없음: 목표만 전달했습니다.
  • 목표 재설명: 같은 목표나 상황을 다시 설명했습니다.
  • 위치 힌트: 메뉴나 영역을 가리켰습니다.
  • 조작 안내: 누를 버튼과 순서를 직접 알려줬습니다.

결과는 “스스로 완료 / 도움받아 완료 / 일부만 해결 / 준비된 설명 없음 / 하고 싶지 않아 종료 / 앱 오류 / 안 함”으로 적습니다. 관심 없는 카드를 지나친 것은 실패가 아닙니다. 앞 과업에서 배운 내용이 다음 과업에 영향을 줬다면 함께 기록합니다.

5. 문제 한 건을 남기는 틀

관찰 ID / 과업 ID / 기기·버전: 시작 화면과 상황: 기대: 무엇을 할 수 있어야 했나요? 실제: 무엇을 눌렀고 어떤 화면이 나왔나요? 재현: 1. 시작 화면 2. 입력·선택 3. 발생 화면 도움: 없음 / 목표 재설명 / 위치 힌트 / 조작 안내 근거: 개인정보를 뺀 발언 요약·화면·발생 횟수. 추정이면 추정이라고 표시 영향: 진행 불가 / 도움·우회 필요 / 불편하지만 완료 해석·개선 후보: 확인할 원인과 바라는 행동 연결: 기존 사용자 이야기·백로그 후보 재확인: 수정 버전 / 같은 경로 결과 / 관련 경로 결과 / 미확인 사항

예시 사실은 “설명 화면에서 홈으로 돌아가 사진 메뉴를 눌렀다”, 해석은 “설명 화면에서 바로 찾는 경로가 잘 안 보일 수 있다”입니다. 실제 관찰 기록이 아닌 작성 예입니다.

사용자 영향이 크다고 개발 순서가 자동으로 정해지지는 않습니다. 발생 근거·구현 범위를 함께 봅니다.

6. 다음 작업과 연결해요

관찰 사실 → 문제 → 바라는 행동 → User Story와 수용 조건 순으로 구체화합니다. 같은 목적의 발견은 기존 백로그에 보완합니다.

설치된 qa 스킬의 기대·실제·재현 형식을 활용했습니다. 이슈가 늘어나지 않도록 이번에는 자동 이슈 생성·세분화를 적용하지 않았습니다. 기록을 정리할 때는 기존 프로토타입 Issue와 기존 관찰 Issue에 연결할 수 있습니다. 이 안내를 만들며 외부 게시를 하지는 않았습니다.

제작자의 기능 확인은 첫 사용 이해의 증거가 아닙니다. 참여자 한 명의 결과는 개선 단서입니다. 전체 방문객의 성공률이나 문화 관심 증가로 일반화하지 않습니다.

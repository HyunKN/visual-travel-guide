# 프로토타입 QA와 사용성 관찰 방법

확인일: 2026-10-17 · 상태: 조사에 따른 운영안. 이 문서 작성은 실제 참여자 관찰을 실시했다는 뜻이 아니다.

사람이 읽을 때는 [간단한 HTML 방법 안내](QA_METHOD.html), 실제 진행·기록은 [테스트 안내와 기록지](TEST_GUIDE.html)를 사용한다.

2026-10-17 사용자 피드백으로 테스트지는 시작 준비·목표·자유 메모 위주로 간소화했다. 진행자가 이 문서의 모든 분류 항목을 현장에서 채우게 하지 않는다. 정확한 조작 순서와 추가 기능 확인은 필요할 때 별도 제작자 점검으로 사용하고, 백로그 판단은 관찰 뒤 정리한다.

## 1. 무엇을 함께 확인하는가?

| 활동 | 확인할 질문 | 담당·방식 | 남길 결과 |
| --- | --- | --- | --- |
| 제작자 기능 확인 | 누르면 약속한 화면과 내용이 나오는가? | 제작자가 정확한 조작 순서로 확인 | 기대 결과, 실제 결과, 재현 순서 |
| 첫 사용 관찰 | 처음 쓰는 사람이 목표에 이르는 길을 이해하는가? | 진행자는 목표를 주고 참여자의 행동을 관찰 | 실제 경로, 망설임, 발언, 받은 도움 |
| 보조 과업 | 첫 시도에서 못 본 기능은 작동하고 이해되는가? | 첫 시도를 끝낸 뒤 순서를 알려 함께 확인 | 도움 후 결과, 추가 문제 |

셋을 넓은 품질 활동으로 함께 운영하되 결과를 섞어 합격 처리하지 않는다.
QA는 절차를 개선하는 활동, testing은 제품을 살피는 활동이라는 구별을 따른다. [ISTQB §1.2.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=17)

## 2. 조사에서 가져온 원칙

- ISTQB: 기능검사는 약속한 기능을 확인한다. 경험 기반 기법 중 탐색적 테스트는 사용하며 배우고 검사하며, 목표를 적은 test charter와 정해진 시간으로 구성할 수 있다. 여기서는 제작자의 짧은 자유 탐색에 적용한다. [§2.2.2·§4.4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=44)
- GOV.UK: 프로토타입에도 진행자 동반 사용성 테스트를 적용한다. 참가자에게 명확하고 중립적인 과업을 주고 행동·생각을 관찰한다. 막히면 도움을 줄 수 있으며 진행 안내를 미리 동료와 연습한다. [공식 안내](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)
- NN/g: 사용자 목표를 현실적인 상황과 실제 행동으로 바꾼다. 조작 단계나 UI 문구를 답처럼 알려주면 스스로 길을 찾는 모습을 보기 어렵다. 명확한 목표를 주는 것과 정답 경로를 알려주는 것은 다르다. [과업 시나리오 작성](https://www.nngroup.com/articles/task-scenarios-usability-testing/)

아래 시간 배분·도움 단계·영향 분류·기록 양식은 위 원칙을 이 프로젝트에 적용한 제안이다. 공인 표준이나 효과가 입증된 수치로 제시하지 않는다.

## 3. 이번 버전의 준비 조건

- 시작은 앱 홈이다. URL은 실행한 기기에 맞게 확인하고, 접속 오류가 있으면 과업을 시작하지 않는다.
- 앱 안에 준비된 사진으로 진행한다. 이번 절차에는 외부 큰 화면·인쇄물·별도 사진·실제 촬영을 사용하지 않는다.
- 진행자 1명과 처음 쓰는 참여자 1명을 기준으로 한다. 제작자 혼자 연습한 결과는 리허설로 표시한다.
- 버전·날짜·기기·브라우저·화면 크기와 사진형/3D형 홈을 기록한다. 이름 대신 참여자 코드로 남긴다.
- S1~S5 ID는 유지한다. 이름 검색은 기존 과업과 섞지 않고 선택적 추가 점검으로 남긴다.
- 준비된 답변·후보·다음 대상을 사용하므로 AI 인식, GPS, 현장 관람 효과를 검증했다고 말하지 않는다.

## 4. 반복해서 쓰는 진행 순서

1. 제작자가 앱이 열리는지와 S1~S5의 참고 순서를 먼저 확인한다. 실행을 막는 오류를 참여자 문제로 기록하지 않는다.
2. 참여자에게 목적과 한계를 설명한다. “앱이 이해하기 쉬운지 보는 자리이고 정답 시험은 아닙니다.”
3. 첫 사용 과업은 시작 화면·상황·목표·끝낼 기준을 읽어준다. 어떤 버튼을 누를지는 먼저 알려주지 않는다.
4. 조용히 관찰한다. 편하면 떠오르는 생각을 말해 달라고 하고, 계속 설명하도록 강요하지 않는다.
5. 참여자가 완료했다고 하거나 그만하려 하면 첫 시도를 끝낸다. 결과와 도움을 먼저 적는다.
6. 더 확인할 필요가 있는 동작만 첫 시도 뒤 함께 확인한다. 안내한 내용과 보조 과업 결과는 메모에 구분해 적는다. 모든 추가 점검을 필수로 시키지 않는다.
7. 관찰 사실과 개선 해석을 나눠 적고 기존 사용자 이야기·백로그 후보와 연결한다.
8. 수정한 뒤 같은 재현 순서와 영향을 받는 이동 경로를 다시 확인한다. 참가자 재관찰 여부는 별도 표시한다.

한 회차는 20~30분 정도로 가볍게 시작하되 피로와 진행 속도에 맞춰 줄인다. 이 시간은 프로젝트 운영 제안이다.
제작자의 탐색 charter 예: “5분 동안 설명→다른 사진→뒤로가기를 살피며 대상·설명이 섞이는지 확인한다.” 시간·범위·확인 목적을 적고 실제 경로와 발견을 남긴다. 이 5분도 우리 제안이다.

## 5. 과업 카드 작성 틀

```text
ID / 사용자 목적:
시작 화면: 홈 / 설명 화면 등 실제 화면 이름
상황: 왜 이 행동을 하려는가?
참여자에게 읽을 목표: 무엇을 알아보거나 선택하면 되는가?
끝낼 기준: 무엇을 확인한 뒤 완료 또는 중단이라고 할 것인가?
진행자용 참고 순서: 시작 화면 → 행동 → 다음 화면 → 끝 화면
추가 점검: 첫 시도 뒤 확인할 출처·관련 질문·뒤로가기 등
```

예: 제작자 S1 리허설은 홈→사진으로 찾기→연못 앞의 장면으로 이동한다. 함께하는 관찰에서는 진행자가 이 사진 선택 화면까지 준비하고 “이 사진 속 건물의 이름과 어떤 곳인지 알아봐 주세요”라고 말한다.
참여자에게 사진 선택 등 정확한 조작 순서를 미리 읽히지 않는다. 사진 준비 도움과 그 이후 조작 도움을 별도로 기록한다. 사전 준비한 홈→사진 이동을 참여자의 독립 발견으로 집계하지 않으며 홈 진입 경로는 먼저 하는 자유 탐색에서 관찰한다.

## 6. 도움과 결과를 적는 법

| 도움 표시 | 진행자가 한 일 | 해석 |
| --- | --- | --- |
| 없음 | 목표만 전달 | 스스로 찾은 경로 |
| 목표 재설명 | 같은 목표를 다시 읽거나 상황을 설명 | 안내 보완 후 진행 |
| 위치 힌트 | 메뉴나 영역을 가리킴 | 경로 발견에 도움 필요 |
| 조작 안내 | 누를 버튼·순서를 직접 알려줌 | 안내를 따른 결과 |

결과는 `스스로 완료 / 도움받아 완료 / 일부만 해결 / 준비된 설명 없음 / 하고 싶지 않아 종료 / 앱 오류 / 안 함`으로 적는다. 관심 없는 카드를 건너뛴 행동은 실패로 보지 않는다.
같은 참여자가 첫 과업에서 배운 내용이 뒤 과업에 영향을 준다는 점을 적는다. 뒤 과업을 모두 독립적인 첫 사용으로 해석하지 않는다.

## 7. 발견 한 건의 기록 틀

```text
관찰 ID / 과업 ID / 기기·버전:
확인한 상황과 시작 화면:
기대: 사용자가 무엇을 할 수 있어야 했나?
실제: 어떤 화면에서 무엇을 눌렀고 무엇이 나타났나?
재현: 1. 시작 화면 2. 입력·선택 3. 발생 화면
도움: 없음 / 목표 재설명 / 위치 힌트 / 조작 안내
근거: 개인정보를 뺀 발언 요약·화면·발생 횟수. 없으면 추정이라고 표시
영향: 진행 불가 / 도움·우회 필요 / 불편하지만 완료
해석·개선 후보: 원인을 확정하지 말고 확인할 가설을 적기
연결: 기존 사용자 이야기 / 기존 백로그 후보
재확인: 수정 버전 / 재현 결과 / 주변 경로 결과 / 미확인 사항
```

예시 사실: “설명 화면에서 다른 사진을 찾으려 홈을 누른 뒤 사진 메뉴를 눌렀다.”
예시 해석: “설명 화면의 바로 탐색 경로가 눈에 덜 띌 수 있다.” 실제 발생 기록이 아닌 작성 예다.
심각도와 개발 순서는 다르다. 우선순위는 사용자 영향·발생 근거·구현 범위를 함께 보고 정한다.

## 8. 백로그·도구에 연결하기

같은 사용자 목적의 발견은 기존 항목에 보완한다. 관찰 사실 → 문제 → 바라는 행동 → User Story·수용 조건 순으로 구체화한다.
스킬 `qa`의 사용자 관점 기대·실제·재현 형식을 활용했다. 자동 이슈 생성·세분화는 사용자의 이슈 증식 방지 요청과 이번 문서 작업 범위에 맞춰 적용하지 않는다.
현재 기록은 [기존 프로토타입 Issue](https://github.com/HyunKN/visual-travel-guide/issues/4)와 [기존 관찰 Issue](https://github.com/HyunKN/visual-travel-guide/issues/13)에 통합할 수 있다. 이 문서 작성으로 외부 이슈를 게시하지 않았다.

제작자 기능 확인 통과는 첫 사용 이해의 증거가 아니다. 참여자 한 명의 결과는 개선 단서이며 전체 방문객의 성공률·문화 관심 증가 근거로 일반화하지 않는다.

## 9. 출처와 적용 범위

- [ISTQB CTFL Syllabus v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf): ISTQB 저작. §1.2.2(p17), §2.2.2(p29), §4.4.2(p44), §2.2.3(p30~31). QA 구별·기능검사·charter·수정 재확인 개념을 짧게 의역했다.
- [GOV.UK — Using moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing): 과업 설계·진행·관찰 안내. 한 명·앱 내부 사진·20~30분 운영은 우리의 조건이다.
- [Nielsen Norman Group — Turn User Goals into Task Scenarios for Usability Testing](https://www.nngroup.com/articles/task-scenarios-usability-testing/): Marieke McCloskey, 2014-01-12. 현실적인 목표와 단계 힌트 방지 원칙. 준비 경로와 참여자 목표를 구분한 S1~S5 구성은 우리의 적용이다.

모든 링크 확인: 2026-10-17. 공식 정의와 프로젝트 운영 제안을 구별하며 원문 자료를 재배포하지 않는다.

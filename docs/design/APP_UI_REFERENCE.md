# App UI 구성 레퍼런스와 두 차례 설계 검토

작성: 2026-11-06. 담당: [후반 UI 작업 #36](https://github.com/HyunKN/visual-travel-guide/issues/36). 사람용 자료: [여섯 화면 HTML 레퍼런스](app-ui-reference/index.html), [실제 캡처·수정 전후 보고서](app-ui-reference/review.html).

## 상태와 읽는 법

사용자 요청은 두 차례 정도 의도·사용자 경험·눈에 띄는 요소·기업 레퍼런스 대비 품질을 검토하고, 구성을 남겨 후속 UI 구현을 유도하는 것이다. 이 문서는 **구조 검토와 두 차례 실제 HTML 화면 검토·수정을 반영한 권장 설계안 R3**다. 디자인 검토·레퍼런스 제작은 수행했으며 사용자 선택, 최종 Android 구현, 두 번의 사용자 테스트, 기업 앱보다 우수하다는 실증 결과와 구분한다.

- 합의된 원칙은 [DESIGN](../DESIGN.md), 기능 경계는 [App 기능 지도 #27](https://github.com/HyunKN/visual-travel-guide/issues/27)과 각 기능 Issue, 공통 사진 결정은 [ADR 0001](../adr/0001-shared-place-photo-anchors.md)을 따른다.
- HTML은 화면·상태·텍스트 위계를 검토하는 독립 문서다. Android 앱·Metro·에뮬레이터를 시작하지 않는다. 별도 서버가 필요 없다.
- 단계별 사례는 문서 내 링크로 이동한다. 실제 native route, 카메라, 인식, 영구 저장, 공개 서버, 자유 사진 확대/이동을 구현했다고 해석하지 않는다.
- 공개 쪽지·추천수는 작성된 디자인 fixture다. 실제 사용자 증언이나 인기 데이터가 아니다. 문서 머리말에 명시한다.
- 검토 근거의 종류: **관찰 기록 / 현재 코드·자료 / 공식 공개 자료 / 설계 추론 / 실행 검사 / 미검증**을 구분한다. AI가 같은 안을 두 번 검토한 것이 독립된 두 사람의 검증은 아니다.

## 1. 목표와 시작 조건

**목표:** 질문을 먼저 생각하지 못한 방문객이 장소의 관람 포인트 하나를 발견하고, 원하면 같은 사진에서 다른 사람의 시선을 읽는다. 현장에서 급히 건물을 알고 싶은 사람은 이야기를 거치지 않고 사진 입력 또는 직접 선택으로 간다.

**현재 기준선:** #28의 기본 UI는 큰 사진 선택 버튼, 같은 형태의 세 장소 카드, 사진 다음에 연속된 설명이다. [사용자가 제공한 상세 화면](app-ui-reference/evidence/user-baseline-detail.png)을 다시 열어 확인했다. 과거 제공 캡처이며 이번에 Android를 실행해 얻은 화면이 아니다. R3는 첫 이야기를 선택해 열고 나머지를 펼치는 방식으로 위계를 바꿨다. 서로 다른 화면 크기·입장 지점이므로 같은 조건의 사용성 비교나 픽셀 일치 검사로 해석하지 않는다.

**사용자 관찰 근거:** [기존 관찰 F02·F05·F06·F10](../prototype/OBSERVATION_RESULTS.md)에서 다음 행동 불명확, 확대 사진과 문서 이동 충돌, 하단 영역 중첩, 첫 유용성 불확실성이 기록됐다. 과거 웹 프로토타입의 결과이며 새 Android 시안의 결함이 재현됐다고 주장하지 않는다.

**해결 방식:** 편집한 콘텐츠 순서·명확한 이동·좌표 변환·복귀 상태는 규칙과 코드로 처리한다. 취향 개인화·자동 부위 인식·사진 간 정합은 이 UI 설계에 추가하지 않는다.

**범위:** #28~34를 연결할 화면과 #36의 시각 기준. 새 Story·SP·공수·계정 기능·검색·지도를 추가하지 않는다. 디자인 후보 작성은 가능하며, Android 최종 적용은 시안 선택과 기능별 준비 상태를 확인한 뒤 한다.

## 3. 권장 화면 구성 R3

### 01 홈

- 64dp 내외 상단 영역: 작은 앱 이름과 최소 48dp의 `사진으로 찾기`. 큰 글자에서는 높이 증가/줄바꿈 허용. 카메라 아이콘만으로 두 입력 경로를 숨기지 않는다.
- 첫 사진은 준비된 실제 사진 전체 비율을 유지한다. 화면을 꾸미려 임의 건물 생성 이미지나 관계없는 이미지로 대체하지 않는다.
- 사진 위 오른쪽 아래 `쪽지 보기`는 공개 글이 있을 때만 제공한다. 본문 카드 안에 중첩한 터치 대상이 아니라 별도 행동이다.
- 바로 아래 장소명·실제 이야기 제목·첫 문장. 예시는 catalog의 `geunjeongjeon-2`. 해당 이야기로 직접 진입하며 처음부터 다른 설명을 보여주지 않는다.
- `장소` 영역에는 세 장소의 이름을 직접 선택할 수 있게 한다. 검색/지도 기능의 대체인 것처럼 포장하지 않는다. 스크롤을 하면 다른 글을 만날 수 있지만 자동 넘김·타이머·새로고침 랜덤화는 없다.
- 방문자 쪽지 미리보기는 최대 하나. 장소와 방문자 글임을 구분하고 누르면 연결된 `sceneId/messageId`로 연다. 읽기 전에 쓰기·로그인을 요구하지 않는다.
- 대표 콘텐츠 순서는 초기 검수 데이터의 편집 순서. 실제 개인화 없이 ‘맞춤’, 위치 없이 ‘주변’, 통계 없이 ‘인기’를 붙이지 않는다.

### 02 이야기

- 장소 이름을 상단에 남기고 선택한 이야기 제목/본문으로 진입한다. 사진·본문은 각각 평면으로 연결하고 큰 회색 카드의 반복을 없앤다.
- 첫 이야기는 펼친다. 다른 이야기는 실제 제목을 가진 펼침 영역. 자동 요약으로 역사적 맥락을 자르지 않는다.
- `쪽지` 진입은 상단과 본문 뒤에서 찾을 수 있다. 동일 행동을 매 단락마다 반복하지 않는다.
- `entryId`, 펼친 항목, 스크롤 위치를 복귀 상태로 유지한다. 출처를 열고 돌아와도 이야기가 바뀌지 않는다.
- 출처는 숨겨진 도움말이 아니라 근거 정보. 읽을 수 있는 대비와 터치 영역을 확보한다.

### 03 공통 사진과 쪽지 읽기

- 사진 전용 화면에는 문서 세로 스크롤을 넣지 않는다. ‘뒤로’와 ‘전체 사진’/‘확대 보기’를 항상 제공한다. 이전 관찰 F05의 스크롤 충돌을 반복하지 않기 위한 후보다.
- R1의 전체 사진 고정안을 수정했다. 가로 2000×1151 사진을 세로 화면에 contain하면 사진이 작고 여백이 크다. R2는 **전용 화면 중앙 확대 → 전체 사진으로 즉시 복귀**를 비교한다. 확대 초기값은 사용자 미승인이다.
- cover에서 사라진 원본 영역이 있음을 인정한다. 전체 보기에서 모든 좌표를 탐색할 수 있어야 하며 숨겨진 표식을 존재하지 않는 글로 처리하지 않는다. 본문 deep link는 해당 원본 좌표를 보이게 이동한 후 연다.
- 이미지 표시와 표식에 같은 변환을 사용한다. 원본을 자르거나 다른 사진으로 바꾸면 새 sceneId를 쓰며, 화면에서의 확대는 같은 sceneId의 표시 상태다.
- 사진 위 흔적은 기본 28dp 내외, 터치는 최소 48dp. 장식으로 위장해 전혀 알아볼 수 없는 표식은 제외. R3는 기존 native 메시지 시안의 말풍선 형태를 재사용했다. 읽는 동안 선택한 흔적만 보이고 다른 표식·작성 행동은 숨긴다. 미세한 표식 디자인은 최종 사용자 승인 전이다.
- 쪽지는 선택 좌표가 아래면 위, 위면 아래에 표시하는 두 위치를 우선 검토. 열고 나면 움직이지 않는다. 긴 글/큰 글자는 가림 최소화보다 읽기·닫기 접근을 우선한다.
- 20dp 외곽, 20dp 안쪽, 20dp 모서리를 출발점으로 한다. 연한 흰색/회색과 약한 blur·테두리·그림자. CSS blur는 Android Liquid Glass 구현 증거가 아니다. 진짜 굴절·성능·대비 조절은 #36에서 확인한다.
- 모달 동안 배경 조작·접근성 탐색 차단, 닫기/Android back/Escape, 선택 표식으로 포커스 복귀. R3는 본문만 스크롤하고 닫기·추천 행은 고정한다. 본문 내부 스크롤과 사진 이동을 동시에 처리하지 않는다.
- 겹친 표식은 기존 [메시지 설계](PLACE_MESSAGES.md)의 grouping 계약을 따른다. 두 fixture의 화면만으로 밀집 사례 통과를 주장하지 않는다.
- 추천은 실제 계약 확정 후 활성화한다. 조회 실패/추천 실패/삭제 글은 각각 구분. 레퍼런스의 두 추천수는 문서 내 토글 예시다.

### 04 위치 선택과 작성

- 사진 전용 선택 상태 → 위치 확정 → 자유 텍스트. 제목·별점·태그·첨부를 필수 항목으로 추가하지 않는다.
- 선택 사진 미리보기와 위치는 동일 scene/anchor. HTML은 한 위치 예시만 표시하며 실제 위치 선택은 구현 전이다.
- 공개 범위는 `나만 보기 / 공개`를 명시적으로 선택하는 안. 비공개 저장 선행을 강제하지 않는다. 초기값·추가 탭 부담은 사용자 결정 항목으로 남긴다.
- 선택 전에는 중립적 완료 이름을, 선택 후에는 `나만 저장` 또는 `공개하기`처럼 실제 결과에 맞는 이름을 쓴다. 로컬 저장 성공을 공개 성공으로 표시하지 않는다.
- 키보드가 열리면 입력 영역이 스크롤 가능하고 완료/뒤로가기가 접근 가능해야 한다. R3 HTML은 축소한 위치 미리보기와 독립된 완료 footer로 처음 화면에서도 완료 행동을 보존한다. 작성 면은 불투명하게, 사진 위치는 키보드로 재계산하지 않는다. 실제 Android 키보드에 대한 증거는 아직 없다.
- 취소·화면 복귀·공개 실패에서 작성 글을 보존한다. 초안 보존 상태와 앱 삭제/익명 세션 소실 시 한계는 #33/#34에서 확정한다.

### 05 사진 입력과 인식 결과

- 제품에서는 촬영·갤러리 선택, 선택 사진 미리보기·바꾸기·지우기, 직접 선택 복구가 필요하다. HTML은 파일 선택만 가능하다.
- 인식 중에는 현재 사진과 취소 동작을 유지한다. 늦은 이전 결과를 현재 선택 위에 덮지 않는다. 임의 퍼센트/가짜 인식 성공은 표시하지 않는다.
- 확정 결과는 장소·검수 이야기로, 보류/실패는 재선택·직접 선택으로 연결한다. 모델 정책과 신뢰도 임곗값은 UI가 임의 결정하지 않는다.
- 갤러리 취소/권한 거부/디코딩 오류는 기존 사진을 유지. 사용자의 원본을 삭제하지 않는다. 위치 없는 입력도 열람을 막지 않는다.

### 06 내 글과 탐색

- `둘러보기 / 내 글` 두 목적지는 Android 최종안의 **제안**이다. 기존 웹의 홈/검색/사진 탐색 결정을 무단 폐기하지 않는다. 선택 후 DESIGN을 갱신한다.
- 하단바는 불투명 흰색, 약 60dp + 시스템 안전 영역. 선택은 명암과 선/아이콘·텍스트로 함께 표시. 사진/읽기/작성 집중 화면에서는 숨긴다.
- 내 글은 #33의 기록을 다시 열고 수정하는 입구다. 프로필·팔로우·새 소셜 피드를 만들지 않는다. 저장 기능 준비 전 비어 있는 목적지를 제품에 먼저 넣지 않는다.
- 타인의 흔적을 리뷰 목록으로 만들지 않는 원칙과, 내 기록을 관리하기 위한 목록은 구분한다. 빈 상태는 짧은 사실과 장소 탐색 행동만 제공한다.

### 실제 화면 검토 1차 — R2 캡처에서 발견한 문제

- [수정 전 작성](app-ui-reference/evidence/before-compose.png): 처음 780px 화면에서 저장 버튼 일부가 잘렸다. 큰 빈 textarea와 전체 너비의 사진이 먼저 공간을 사용했다. 사진을 230px 너비로 줄이고 입력 기본 높이를 180px로 낮췄다. 완료 행은 스크롤 밖에 둔다.
- [수정 전 큰 글자](app-ui-reference/evidence/before-compose-large.png): 글자 200%에서 빈 입력칸이 화면 대부분을 차지했다. 입력 자체는 스크롤하되 완료 행동은 항상 남는 구조로 보완했다.
- [수정 전 읽기](app-ui-reference/evidence/before-reader.png): 읽는 동안 다른 표식과 글쓰기 행동이 경쟁했다. 선택 위치만 남기고 배경 조작을 비활성화했다. 표식의 ‘글’ 글자를 기존 시안의 말풍선 형태로 교체했다.

### 실제 화면 검토 2차 — 수정본과 반례

- [작성 200%](app-ui-reference/evidence/04-compose-large.png): 내용·공개 범위·완료 버튼을 볼 수 있고 스크롤 영역과 고정 완료 행이 분리돼 있다. 브라우저에서 버튼의 bounding box가 phone 안에 있음을 검사했다.
- [긴 쪽지](app-ui-reference/evidence/03-reader-long.png): 전체 패널 스크롤 방식은 긴 글에서 닫기를 잃을 수 있어, header/footer를 고정하고 본문만 스크롤하도록 추가 수정했다. 긴 글 55회 반복 후 끝으로 스크롤한 상태에서 닫기·추천이 패널 안에 남는다.

**화면 검토 결론:** 사진·텍스트 위계와 쪽지의 장소 맥락이 구체화됐고 발견한 가림/복귀/입력 문제를 수정했다. 범용 카드 목록보다 우리 과업에 맞는 구성으로 추천한다. 하지만 선호·관심·현장 편의가 기업 앱보다 더 좋다는 결론은 실제 사용자 비교 없이 내리지 않는다. 이 결론 자체를 비교 검토 결과로 남기며, ‘무조건 더 좋다’는 통과 판정으로 바꾸지 않는다.

### 6.1 폰트·색상·기술·모션 상세 사양

2026-11-06 후속 요청으로 추가한 **Android 적용 전 제안**이다. 기존 HTML의 160ms 예시와 캡처는 그대로 보존하며, 아래 값까지 실행 검증됐다는 뜻은 아니다. 사진 속 장소와 방문자의 시선을 연결하고 조작 결과를 알아보기 쉽게 하는 것이 목적이다.

#### 폰트와 색상

합의한 **원본 Spoqa Han Sans Regular/Bold**를 유지한다. Neo·Pretendard로 바꾸지 않는다. 웹용 파일·출처·OFL은 [기존 fonts](../../prototype/src/fonts/SOURCE.txt)에 있다. 현재 native 소스에는 `fontFamily` 지정이 없고 [앱 설정](../../mobile/app.json)의 `expo-font`에는 파일 매핑이 없다. 설치와 실제 적용은 다르다. Android에는 같은 원본 계열의 정적 TTF/OTF를 확보해 400/700을 매핑하고 라이선스를 보존한다. WOFF2를 그대로 복사하지 않는다. [Expo 지원 형식](https://docs.expo.dev/develop/user-interface/fonts/), [SDK 57 font 설정](https://docs.expo.dev/versions/v57.0.0/sdk/font/).

#### UI 구성 기술과 현재 상태

2026-11-06 [package.json](../../mobile/package.json)과 실제 소스를 확인했다. Expo 57, RN 0.86, Reanimated 4.5.1이 현재 기반이다. 아래 후보를 위해 설치·빌드·앱 실행을 하지 않았다.

| UI | 구현 방법 / 후보 | 상태와 남은 일 |
| --- | --- | --- |
| 글자·버튼·입력·평면 하단바 | RN Text/Pressable/TextInput/View, safe-area | 기존 기능 코드를 공통 토큰으로 정리. K-style CSS를 RN에 직접 적용하지 않음 |
| 화면 이동 | Expo Router/native Stack | 사용 중. 기본 전환 위에 별도 진입 효과를 중복하지 않음 |
| 사진·쪽지 표식 | Image + 같은 좌표 변환 + Pressable | `sceneId + u/v` 유지. 움직일 때도 사진과 표식 변환 일치 |
| 눌림·쪽지 열림·선택 | Reanimated shared value/animated style/withTiming | 라이브러리 설치됨. 아래 모션의 화면 적용은 예정 |
| 유리 쪽지 | 현재 사진 복제 blurRadius + 흰 tint. 배경 blur 후보 expo-blur | [현재 시안](../../mobile/src/features/place-message-preview/PlaceMessagePreview.tsx)은 굴절 없음. expo-blur 미설치, native 추가 시 재빌드 필요 |
| 정교한 굴절·테두리 광학 | 별도 렌더링 실험 후보 | Skia 등 미설치·미채택. 기본 blur와 시각·성능을 비교한 뒤 결정 |
| 뼈대 로딩 | Skullet 형태를 RN View로 각색, 필요 시 Reanimated opacity | 실제 기다리는 영역만. Skullet RN 직접 호환성 미확인. 로컬 콘텐츠에 가짜 로딩 없음 |
| 앱 소개용 모션그래픽 | 별도 HTML 시간축·영상 제작 후보 | 앱 조작과 분리. Remotion/Lottie/Rive를 지금 제품 의존성으로 추가하지 않음 |

[SDK 57 BlurView](https://docs.expo.dev/versions/v57.0.0/sdk/blur-view/)는 Android에서 BlurTargetView 연결을 요구하고 SDK 31 미만의 성능 비용과 blur 없는 대체 경로를 설명한다. 구형 기기는 불투명 대체부터 비교한다. [GlassEffect](https://docs.expo.dev/versions/v57.0.0/sdk/glass-effect/)는 iOS native 효과이며 지원하지 않는 플랫폼에서는 일반 View로 대체된다. 설치만으로 Android Liquid Glass가 생기지 않는다. **유리 쪽지 요구는 유지하되 광학 효과·실기기 성능은 미검증**이다.

#### 동작별 모션 제안

| 동작 | 시작 → 끝 / 시간 | 중단·접근성·실패 처리 |
| --- | --- | --- |
| 일반 버튼 | scale 1 → .98, 100ms / 복귀 140ms | 누름 취소도 복귀. 모션 완료를 기다려 요청하지 않음 |
| 작은 유리 조작부 | scale 1 → 1.025, 100ms / 복귀 180ms | 기존 재질의 미세한 부풀림 방향. 본문 전체를 출렁이게 하지 않음 |
| 쪽지 열기 | 선택 즉시 강조, opacity 0 → 1, y 8 → 0, 220ms | 시작부터 배경 조작 비활성·닫기 접근. 사진 고정, 글자별 등장 없음 |
| 쪽지 닫기 | opacity 1 → 0, 140ms | 종료 후 선택 표식에 포커스 복귀. 열림 도중 닫아도 잔상·투명 차단층 없음 |
| 다른 쪽지 | 내용 교체 fade 120ms | 오래된 응답이 새 선택을 덮지 않음. 추천은 messageId별 상태 |
| 추천 | 선택색 120ms, 아이콘 반응 160ms 이내 | 실패 시 값·색 복구, 중복 요청 방지. 폭죽·큰 숫자 튀김 없음 |
| 사진 로드 완료 | 자리 확보 후 opacity 0 → 1, 180ms | 비율 유지. 오류 시 재시도, 이전 사진 선택 보호 |
| 뼈대 로딩 | opacity .55 ↔ 1, 1200ms 주기 | 준비 즉시 종료·앱 비활성 시 정지. 동작 감소는 정지 면. 가짜 진행률 없음 |
| 이야기 펼침·이동 | 즉시 펼침 / native 이동 기본값부터 | 스크롤·읽기 순서 보호. 긴 본문 높이·타이핑 효과 제외 |

기본 easing 후보는 진입 `bezier(.2, 0, 0, 1)`, 종료 `bezier(.4, 0, 1, 1)`이다. 레퍼런스에서 측정한 수치가 아니라 비교 출발값이다. transform/opacity 중심으로 구성하며 큰 blur·그림자를 매 프레임 변경하지 않는다. 읽는 동안 반복 발광·자동 줌·패럴랙스는 사용하지 않는다. 탄성은 필요성이 확인된 조작부만 다음 비교 단계에서 조정한다.

동작 감소는 [Reanimated ReduceMotion.System](https://docs.swmansion.com/react-native-reanimated/docs/animations/withTiming/)과 연결한다. 크기·이동·반복을 제거해도 같은 상태·행동을 제공한다. 투명도 감소는 별도 재질 정책이며 Android OS 신호를 자동 수신한다고 가정하지 않는다. 불투명 대체를 유지한다.

작은 코드 예제 — **설계 예제로 실제 앱에 추가하거나 typecheck한 코드가 아니다.** 상태·포커스·종료 처리는 기존 화면에 맞춰 함께 구현한다.

```ts
const motion = { readerEnter: 220, readerExit: 140, readerOffset: 8 };
// progress는 useSharedValue(0). style은 useAnimatedStyle에서 계산한다.
progress.value = withTiming(open ? 1 : 0, {
  duration: open ? motion.readerEnter : motion.readerExit,
  easing: open ? Easing.bezier(.2, 0, 0, 1) : Easing.bezier(.4, 0, 1, 1),
  reduceMotion: ReduceMotion.System,
});
// opacity: progress.value, translateY: (1 - progress.value) * motion.readerOffset
```

빠른 열기/닫기는 현재 진행값에서 반대 방향으로 전환한다. 오래된 완료 콜백이 새 reader를 해제하지 않도록 현재 상태를 확인한다. 모션 완료를 저장·추천 성공으로 처리하지 않는다. 터치·접근성 상태는 시각 효과와 별도로 관리한다.

#### 제공받은 레퍼런스의 활용

- [Prompt Motion](https://prompt-motion.com/)은 영상과 프롬프트·스킬을 연결하는 사례 모음이다. [Meng To HTML app demo](https://prompt-motion.com/mengto-a7f4679)는 React 기반 데모를 하나의 시간축에서 반복·탐색·정지하는 방식으로 소개한다. 소개문을 확인했으며 스킬 설치·코드 검증·영상 전체 분석은 하지 않았다. 검토용 모션을 같은 시작/중간/끝에서 비교하는 방법으로 참고한다.
- [BUGI 게시글](https://x.com/Bugi952/status/2118290476722000151/video/1)은 모션 사례를 익혀 다음 제작에 재사용한다는 취지의 본문을 확인했다. 영상은 브라우저에서 ‘미디어를 재생할 수 없습니다’로 표시됐고 재생 시도 후에도 같았다. 타이밍·기법·제작 도구를 추측해 채택하지 않는다. 영상 파일 확보 시 분석한다.
- 우리 기록 단위: `원본 URL·확인 범위 → 필요한 사용자 행동 → 시간·거리·easing → RN 코드 → 취소/감소/오류 → 검토 결과`. 모델을 재학습했다는 뜻이 아니라 저장소 규칙과 재사용 구현으로 남긴다.
- 홍보 영상의 연출을 매번 기다려야 하는 앱 진입 영상으로 가져오지 않는다. 외부 프롬프트·스킬은 자료이며 프로젝트 지침을 덮어쓰지 않는다. 코드 복사 시 원본 라이선스를 별도로 확인한다.

**후속 순서:** 폰트·색상 토큰 → 한 쪽지 열림/닫힘 → 일반/감소 모션·긴 글·연타·뒤로가기 → 같은 Android 기기의 blur 없는 기준선과 비교 → 선택된 패턴 확장. 취소·실패 복구, 입력 보호, 포커스 복귀를 확인한다. 실기기 빌드 종류·OS·화면 주사율·동작별 프레임 지연을 기록하며 60/120fps를 사전 보장하지 않는다. 기존 15개 HTML 검사를 새 폰트·모션 검증으로 계산하지 않는다. 진행·인수 원본은 #36이다.

## 7. 후속 개발자가 이 레퍼런스를 쓰는 방법

1. DESIGN의 합의와 이 문서의 ‘후보’를 구분한다. 대표 콘텐츠 배치·2탭·초기 확대·공개 범위 선택은 사용자 선택을 먼저 기록한다.
2. HTML을 브라우저에서 직접 열어 정상/큰 글자/불투명 상태를 비교한다. 앱·에뮬레이터·서버 실행은 사용자가 한다.
3. 화면 하나씩 승인된 구성으로 RN에 옮긴다. HTML/CSS·DOM 모달을 RN에 붙여 넣지 않는다. 콘텐츠/ID/좌표/입력/저장 모듈은 재사용한다.
4. 함수 위치는 실제 구현 후 #36에 갱신한다. 예정 구성은 `DiscoveryHome`, `PlaceStory`, `SceneCanvas`, `MessageReader`, `MessageComposer`, `PhotoInputScreen`, `MyNotes`. 이름을 위해 기존 기능 모듈을 중복 생성하지 않는다.
5. 입력: 검수 `placeId/entryId/assetId`, 공개 `sceneId/messageId/anchor`, 로컬 draft. 출력: 선택/이동/저장 의도. 화면이 API 결과를 성공으로 위조하거나 저장소를 직접 복제하지 않는다.
6. 사진→설명, 쪽지 열림/닫힘, 뒤로가기, 실패→재시도, 큰 글자, 키보드 상태를 같은 화면 크기의 캡처로 대조한다. 필요한 근거를 #36에 연결하고 사람 확인 전 닫지 않는다.

**구현 프롬프트로 재사용할 문장:**

> DESIGN과 APP_UI_REFERENCE의 승인된 항목만 적용한다. 실제 장소 사진과 기존 스포카/K-style 토큰을 사용한다. 홈의 첫 이야기와 직접 탐색, 사진에 고정된 쪽지의 관계를 유지한다. 태그라인·도움말을 추가해 조작 문제를 가리지 않는다. 긴 글·큰 글자·권한 거부·빈 결과·오래된 응답·뒤로가기·작성 내용 보존을 포함한다. Android 실제 화면을 기준으로 검증하고 웹 시안/fixture를 제품 완료로 보고하지 않는다. 앱 실행은 사용자가 한다.

## 8. 비교 관찰과 완료 조건

### 디자인 품질 확인

- 동일 콘텐츠로 #28 기본 화면과 R2를 비교한다. 상용 앱은 같은 과업을 지원하지 않을 수 있으므로 홈 위계·시트 닫기·본문 가독성 같은 공통 요소만 비교한다.
- 360/390/430 너비, 글자 100/200%, 긴 장소명·긴 쪽지, 밝은 하늘·복잡한 단청·짙은 배경을 사용한다. 기본 안이 조건 중 하나에서 글/행동을 잃으면 보완한다.
- 렌더 확인 전 ‘예쁘다’, ‘시선이 간다’, ‘동등 이상’ 같은 평가를 통과로 표시하지 않는다. 부드러움은 실제 Android 프레임·입력 결과가 필요하다.

### 실제 사용자에게 물어볼 과업

1. 첫 화면만 보고 무엇을 할 수 있는지, 누르면 무엇이 나올지 말해 달라고 한다. 진행자가 조작법을 먼저 알려주지 않는다.
2. 이름을 모르는 건물을 알아보려는 상황과, 아무 질문 없이 둘러보는 상황을 각각 준다. 사진 입력/직접 선택/이야기 탐색 경로를 기록한다.
3. 방문자 글을 열고 사진으로 돌아온 뒤 원래 보고 있던 대상을 다시 찾게 한다. 사용자가 안 열고 싶다고 하면 거부 이유도 기록한다.
4. 글을 쓰다가 돌아갔다가 다시 열게 하고, 공개/나만 보기 선택 결과를 예상하게 한다. 원하지 않은 공개·입력 소실은 실패다.
5. 기준선과 순서를 바꿔 비교한다. 우수성 판정은 성공/실수/도움 요청/자발적 다음 행동/거부 이유를 함께 본다. 시간이 짧아진 것만으로 흥미를 입증하지 않는다.

목표: 새로운 치명적 실패(읽기 불가, 복귀 실패, 잘못된 공개, 입력 소실) 없이 처음의 행동을 이해하고 장소를 다시 살펴보는 경험. 최소 효과 크기·참여자 수는 사용자와 평가 계획에서 정하며 근거 없이 성공률을 정하지 않는다. 레퍼런스 열람만으로 기업 앱 대비 우위를 확정하지 않는다.

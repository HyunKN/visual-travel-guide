## 2. Sprint Goal

> 첫 적용 사례인 경복궁에서 방문객이 지원 장소를 알아보고 자신의 시선을 기록한 뒤, 같은 장소의 다른 사람 흔적을 만나며 관심에 따라 관람을 이어갈 수 있다.

장소 탐색·기록·공유 서비스의 첫 적용 범위는 근정전·교태전·광화문 3곳이다. 다른 장소는 자료를 준비하고 인식을 검증한 뒤 확대한다.

## 4. SP vs Capacity 검증

| 항목 | 내용 |
| --- | --- |
| ① 선택 SP 합계 | 50 SP |
| ② 팀 velocity 가정 | 약 0.94h/SP (47h ÷ 50 SP, 실측 전) |
| ③ 추정 공수 (① × ②) | 47h (Story별 작업 37h + 공통 작업 10h) |
| ④ 팀 Capacity (§1.1) | 60h (평일 3h·주말 5h) |
| ⑤ 버퍼 (④ - ③) | 13h / 약 21.7% |
| ⑥ 판정 | 초기 추정 · 인식·공유 연동 후 실제 잔여 재산정 |

후순위 2개 항목의 작업 4h를 제외해 예비 13h를 확보한다. 권장 비율보다 큰 예비는 행사와 인식·공유 연동 변동에 대비한다.

## 6. Risk Analysis

| Type<br>(기술/일정/팀) | Description | Impact<br>(H·M·L) | Mitigation (대응) | 담당 |
| --- | --- | --- | --- | --- |
| 인식·자료 | S3 연결 및 교태전 등록 사진의 구별 성능 | H | 11/1까지 S3 ONNX 파일·전처리·출력을 확인한다. 교태전은 등록 사진 비교와 별도 평가로 검증하며 기존23개 클래스의 정확도를 전용하지 않는다. 실패 시 범위·잔여를 조정한다. | 개발자 |
| 공유·권한 | 익명 사용자 식별과 공개 글 접근 제어 오류 | H | Supabase 익명 인증과 작성자·공개 상태별 RLS를 구성한다. A/B의 무단 수정·삭제 거부 및 신고·숨김을 검사한다. 비공개 사진은 전송하지 않는다. | 개발자 |
| 일정·기기 | 11월2주차 행사·참여자 기기 확보 지연 | H | 13h 예비로 일정 변동에 대응한다. 11/8까지 참여자 Android 기기 사전 확인, 11/12 기능 범위 고정. 초과 시 실제 잔여와 우선순위를 다시 판단한다. | 개발자 |
| 사용성·현장 | 기록 부담·사진별 흔적 위치·현장 방문 제약 | M | 최소 2명에게 같은 장소에서 기존 검색·상용 AI와 비교하도록 한다. 새로 알게 된 점·다음 장소에서 쓸 방식과 이유·기록 중 막힌 행동을 확인한다. 현장이 어려우면 권리·정답을 확인한 사진으로 모의 평가하고 현장 효과와 구분한다. | 개발자 |

흔적은 사용자 사진 위에서 같은 장소의 메모를 확인하는 방식이다. 특정 창문·기둥 등 부위에 고정하지 않으며, 표시 모양은 UI 설계에서 정한다.

기술 선정: S4와 성능 차이가 작고 모델 규모가 작은 MobileCLIP2-S3, 기존 ONNX 모델을 활용할 ONNX Runtime, 공유 글 저장과 사용자별 접근 제어를 지원하는 Supabase를 채택한다.
